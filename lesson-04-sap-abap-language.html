Lesson 4 — SAP ABAP Language

Every screen you used in Lesson 3 — FB50, F-02, FS10N — was written by someone, in a language. That language is ABAP, SAP's own programming language. 01 Quick recap of Lessons 1–3

Thirty seconds of revision, then we go one layer deeper.

  • Lesson 1 — Introduction: SAP is an ERP (one shared software for the whole company). S/4HANA is SAP's newest ERP, running on the fast HANA database. FICO = FI (Financial Accounting — the legal books) + CO (Controlling — internal cost analysis).
  • Lesson 2 — Architecture: SAP has three layers — Presentation (your screen), Application (the brain that runs programs), Database (where data is stored). Systems come in a line: DEV → QAS → PRD, and changes travel between them in Transport Requests.
  • Lesson 3 — Interface: You log on through SAP GUI or Fiori, jump with T-codes in the command field, read messages in the status bar (S–I–W–E–A–X), and rescue yourself with F1 (help) and F4 (list of values).

One question was left open at the end of Lesson 3: who writes the programs behind those screens — and in what? That is today's lesson. (Screens ke peeche jo programs chalte hain, wo kis language mein likhe jate hain? Jawab: ABAP.)

02 What is ABAP?

One full form, one simple meaning, one short history.

New term — ABAP

ABAP = Advanced Business Application Programming. In simple words: the programming language in which SAP software itself is written — and in which companies write their own extra programs inside SAP. Almost every screen, check and calculation in FI, MM, SD and HR is ABAP code written by SAP.

(ABAP wo zuban hai jisme khud SAP software likha gaya hai — jaise kisi building ki neev aur deewarein.)

Think of it like this. A programming language is a set of strict instructions a computer can follow — like a recipe written so precisely that even a machine cannot misunderstand it. Different software is written in different languages: Windows is mostly C++, websites often use JavaScript. SAP chose to build its business software in its own language, ABAP, because business programs mostly do three things — read data from tables, apply rules, and show or save results — and ABAP is specially designed for exactly that.

Analogy — the factory and its own workshop

Imagine a huge factory (SAP) that makes furniture. The factory also has its own workshop with its own tools inside the building (ABAP). The furniture (SAP standard programs) was built with those tools — and if you, the customer, want a special cupboard (a custom report), the factory's carpenters build it with the same tools, in the same workshop, so it fits perfectly with everything else. ABAP is not an outside add-on; it is SAP's own workshop language.

A very short history (only what the exam expects)

  • 1980s: ABAP begins as a simple report-writing language — its first job was printing lists from SAP data. (Old-timers still call every ABAP program a “report” for this reason — remember this, it explains SAP vocabulary later.)
  • 1990s (R/3 era): ABAP grows into a full language that builds screens, transactions and business logic — the whole of R/3 and later ECC is written in it.
  • 2000s: ABAP gains object-oriented features (ABAP Objects — programs organised into “classes”, like templates that create working copies; more in Section 10).
  • S/4HANA era: ABAP is modernised for HANA — heavy calculations are pushed down into the database (Section 15), and new tools like CDS views appear.
Memory trick — the full form

Advanced Business Application Programming → remember: “A Business Application Program.” ABAP exists for business applications — not games, not operating systems. If an exam option says ABAP is a database, a hardware or an operating system — it is wrong. ABAP is a language.

Three facts to fix in your mind

  1. SAP is written in ABAP. When you post with FB50, ABAP code checks your entry, calculates tax, assigns the document number and saves it.
  2. Customers also write ABAP — for their own reports, printouts and extra checks. These are called custom developments or Z-programs (Section 13 explains the Z).
  3. ABAP is a “4GL”. Exam word ABAP is called a fourth-generation language (4GL) — a high-level language close to business thinking (“read this table, total this column”) rather than close to the machine. That is why ABAP code reads almost like English sentences.

03 Why an FI consultant needs ABAP

You are preparing for an FI certificate, not a programming job. So why this lesson? Four very practical reasons.

Situation in real projectsHow a little ABAP saves you
1. Writing a specification (spec)When the business asks for a new report, you write the requirement document for the ABAP developer. If you can name the exact tables and fields (“take document header from BKPF, amounts from ACDOCA”), the developer builds it right the first time.
2. Finding why something went wrongAn error message appears during posting. With /h debugging (Section 14) you can watch where the program stopped — often you find it is a missing setting, not a program bug, and you fix it yourself in minutes.
3. Checking data directlyNo report shows what you need? Open the table in SE16N and look at the raw data yourself, instead of waiting days for a report.
4. Talking to the technical teamProjects fail on misunderstandings. A consultant who knows words like function module, BAdI, transport, workbench gets correct estimates and correct solutions.
New terms — functional vs technical consultant

A functional consultant (your path — FI/CO) knows the business process and the SAP settings (configuration / customizing). A technical consultant (an ABAPer) writes code. Big projects need both. You are not crossing over — you are learning enough of their language to work together. (Aap coder nahi ban rahe; aap wo consultant ban rahe hain jo coder ko sahi kaam de sakta hai.)

Exam trap

C_TS4FI is a functional exam. It will not ask you to write ABAP code. But it can ask what ABAP is, what the Data Dictionary does, or which tool displays table contents. Learn the concepts and T-codes in this lesson; do not memorise code syntax beyond recognising the handful of words in Section 9.

04 Where ABAP lives and runs

Connecting Lesson 2 (architecture) with today's language — three simple steps from typed code to running program.

Recall the three layers: Presentation, Application, Database. ABAP belongs to the Application layer. Here is the life of an ABAP program:

New terms — source code, compiler, runtime

Source code = the human-readable text of a program. Compiler = the translator that checks that text and converts it into a form the machine can execute quickly. Runtime (ABAP runtime environment) = the part of the application server that actually executes the program when a user runs it — like the player that plays a recorded song. In SAP, compiling happens automatically the first time a program runs after a change; you never press a separate “compile” button.

Two more ideas that complete the picture

  • The Repository — every ABAP program, table definition and screen is stored as an object in a central library inside the database called the Repository. (Repository = SAP ki markazi library, jahan har program aur table ki definition mehfooz hai.) Repository objects are client-independent (Lesson 2): a program written in client 100 exists for all clients of that system.
  • The kernel — underneath ABAP sits the kernel, the core engine of the application server, written in C/C++. The kernel is SAP's platform software; ABAP programs run on it. You never write kernel code — just remember the layering: ABAP programs → ABAP runtime → kernel → operating system → hardware.
Analogy — recipe, chef and kitchen

Source code is the recipe card. The compiler is the head chef checking the recipe for mistakes before cooking starts. The runtime is the cook actually preparing the dish each time an order comes. The kernel is the kitchen itself — stoves, knives, gas supply. And the Repository is the recipe book where all cards are filed.

05 The ABAP Workbench — the programmer's toolbox

A “workbench” is simply the set of built-in tools used to build and repair ABAP objects. You already know several of its doors from Lesson 3 — they are ordinary T-codes.

New term — ABAP Workbench

The ABAP Workbench is the collection of SAP's own development tools — editor, dictionary, object browser and testers — all inside SAP itself. A developer does not use outside software to write ABAP; the tools live within the SAP system (in DEV). Modern developers may also use ABAP Development Tools (ADT) — ABAP editing inside the Eclipse program on their PC — connected to the same system.

06 The Data Dictionary (DDIC) — the master book of definitions

If ABAP is SAP's language, the Data Dictionary is its official dictionary — the single place where every table and field is defined, once, for everyone.

New term — Data Dictionary (DDIC)

The ABAP Data Dictionary (T-code SE11, short name DDIC) is the central register that defines what data exists and what it looks like: every table, every field in it, each field's type (text? number? date?) and length, and how fields relate to each other. Programs do not invent their own definitions — they borrow them from the Dictionary. Change a definition in the DDIC, and every program using it sees the change.

(DDIC wo markazi register hai jahan har table aur field ki tareef ek hi dafa likhi jati hai — phir saare programs wahi tareef istemal karte hain.)

Analogy — the land registry office

In a city, the land registry holds the official record of every plot: its size, boundaries and owner. Builders, banks and buyers all trust that one record instead of measuring the land themselves each time. The DDIC is SAP's registry office: the official record of every “plot of data” — its size (length), its type (residential or commercial = text or number) and its boundaries (allowed values).

The three building blocks: domain → data element → table field

This chain is small, logical, and a favourite exam topic. Read it bottom-up with one real FI field — the company code field BUKRS:

ObjectSimple meaningAccounting example
DomainThe technical shape of a value: data type (CHAR/NUMC/DATS/CURR…), length, and sometimes a list of allowed values. No description text.Domain BUKRS: characters, length 4.
Data elementThe business meaning of a field: it uses one domain and adds the labels you see on screens (“Company Code”) in every language.Data element BUKRS = “Company Code”.
Transparent tableA real database table with rows and columns, defined in the DDIC — “transparent” because the DDIC table and the database table are one and the same.BKPF, BSEG, ACDOCA (next section).

New terms — data types you will meet in FI tables

CHAR = text of fixed length · NUMC = text that holds only digits (document numbers are NUMC — that is why document 123 shows as 0000000123) · DATS = a date stored as YYYYMMDD · CURR = a money amount (always paired with a currency field) · QUAN = a quantity (paired with a unit). When you browse a table in SE16N and see dates as 20261126, you now know why.

Exam trap — domain vs data element

The exam loves this pair. Domain = technical (type + length). Data element = semantic / business (meaning + labels). A domain can be reused by many data elements; a field gets its screen text from its data element, never from the domain. And remember: the DDIC holds definitions; the data itself lives in the database tables those definitions describe.

07 FI tables you already know: BKPF, BSEG, ACDOCA

Now the payoff for an accountant: when you post a journal entry in SAP, where does it physically go? Into tables — and you already understand their shape from paper accounting.

Analogy — the bound journal register

In a manual system, the journal register has one line per entry in the day book, and the full detail follows underneath. SAP copies this exactly: BKPF is the register's summary line (one row per document — the header), and BSEG holds the detail lines underneath it (one row per line item — debit this, credit that).

Memory tricks — table names have a pattern

BKPF ends in F and holds the kopf (German for “head” — header!). BSEG = SEGment. Master tables: …A1 = general data, …B1 = company-code data (LFA1/LFB1, KNA1/KNB1, SKA1/SKB1). And the key of almost every FI document is the trio BUKRS + BELNR + GJAHR — company code + document number + fiscal year. That trio will follow you through the whole course.

Try the idea: browsing a table with SE16N

In a training system you would type SE16N, enter table BKPF, set BUKRS = 1000, and press Execute — SAP shows the actual document headers as a grid. No code, no developer. This single skill — checking the table yourself — is used by real FI consultants every week, for example to confirm whether a document really exists, or which user posted it.

Exam trap — BSEG in S/4HANA

In S/4HANA, ACDOCA is the single source of truth for journal lines, and many old “totals” and “index” tables of ECC no longer exist as physical tables. BSEG still exists and still holds document line items — do not let an option tell you BSEG was deleted. What changed is that reports now read ACDOCA, and old tables like BSIS/BSAS are delivered as compatibility views that read ACDOCA behind the scenes.

08 Reading ABAP: anatomy of a small program

Goal: read, not write. Here is the SE38 program from Section 5 again — now taken apart line by line, in accountant's language.

ABAP Editor (SE38) — program ZFI_TRIAL_BALANCE — illustration, not a real SAP screenshot
REPORT zfi_trial_balance.

DATA: gv_bukrs TYPE bkpf-bukrs.

SELECT bukrs, belnr, gjahr, budat
FROM bkpf
INTO TABLE @DATA(lt_docs)
WHERE bukrs = '1000'.

LOOP AT lt_docs INTO DATA(ls_doc).
WRITE: / ls_doc-belnr, ls_doc-budat.
ENDLOOP.
LineWhat it says, in plain English
REPORT zfi_trial_balance.“This program is a report, and its name is ZFI_TRIAL_BALANCE.” Every executable program starts by declaring itself. (The Z is explained in Section 13.)
DATA: gv_bukrs TYPE bkpf-bukrs.“Reserve a box (a variable) named gv_bukrs. Its shape must be exactly like the BUKRS field of table BKPF.” Notice: the program borrows the DDIC definition — Section 6 in action. Change the field in the Dictionary, and this variable changes too.
SELECT … FROM bkpf … WHERE bukrs = '1000'.“From table BKPF, fetch the columns company code, document number, year and posting date — but only rows where company code is 1000 — and put them into a list in memory called lt_docs.” This reading of the database is called Open SQL (next box).
LOOP AT lt_docs … ENDLOOP.“Take the fetched list and go through it one row at a time, from first to last.” Between LOOP and ENDLOOP sits what to do with each row.
WRITE: / ls_doc-belnr, ls_doc-budat.“Print, on a new line, this row's document number and posting date.” WRITE is the oldest ABAP output command — a leftover from ABAP's report-writing childhood.
New terms — variable, internal table, work area, Open SQL

A variable is a named box in memory holding one value while the program runs. An internal table is a list of rows held in memory only (it vanishes when the program ends — it is not a database table; this confusion is a classic exam trap). A work area is a single-row box used to hold the row currently being processed inside a loop — like the one line of the register your finger is on. Open SQL is ABAP's own database language: the ABAP runtime translates it into whatever the real database (HANA, Oracle…) speaks, so the same program works on any database.

Analogy — the accountant and the filing cabinet

SELECT is walking to the filing cabinet (database) and pulling out a bundle of files (internal table). LOOP is going through the bundle file by file. The work area is the one file open on your desk right now. WRITE is noting its number in your notebook. When you finish and go home (program ends), the bundle on the desk disappears — the cabinet (database) is untouched unless the program explicitly saves changes.

You do not need a hundred commands. These few cover most of the FI-related code you will ever be shown in meetings, specs and error messages.

Memory trick — naming habits tell you the type

Developers name things with prefixes: g = global, l = local, t = table, s = structure/work area, v = variable. So lt_docs = local table of documents, ls_doc = local structure (one row), gv_bukrs = global variable. These are conventions, not rules — but once you see them, ABAP code stops looking like alphabet soup. (Naam ke pehle harf hi bata dete hain ke ye table hai, row hai ya sirf ek value.)

“Program” is only one member of the family. Meet the relatives — each with one simple job.

Analogy — blueprint and houses (classes & objects)

An architect's blueprint is the class: it defines rooms, doors and wiring once. Each house built from it is an object: same design, but each has its own occupants and furniture (its own data). Programs mostly work with houses; architects (senior developers) design blueprints. You only need the idea: class = template, object = a live copy.

New term — dynpro

A dynpro (“dynamic program”) is the technical name of an SAP GUI screen — the fillable form part of a module pool program, numbered (e.g. screen 0100). When an error message says “dynpro not found”, it simply means: a screen of the program is missing. One more German-flavoured word decoded.

11 Forms: printouts, invoices and cheques

Accountants live on paper (and PDF): invoices, payment advices, cheques, dunning letters. In SAP, the layout of every such printout is a “form” — and form technology is pure exam vocabulary.

TechnologyEraOne-line truth
SAPscriptOldest (R/2–R/3)The original form tool (SE71). Still found in old systems; painful to change.
Smart FormsMiddle (from ~2000)Graphical form builder (SMARTFORMS) — drag-and-drop layout, generates a function module behind the scenes.
Adobe Forms (Interactive Forms by Adobe)Current standardPDF-based forms designed in Adobe LiveCycle Designer; the standard choice in S/4HANA for invoices and statements. Output is a real PDF.

How a printout is born, in four steps: (1) a program (often the standard posting/payment program) collects the data; (2) it calls the form with that data; (3) the form lays the data into the design — logo, address, lines, totals; (4) the result goes to the printer or becomes a PDF/email. When the business says “our logo is wrong on the invoice”, the fix is in the form, not in the posting program — knowing which layer to ask for is exactly the kind of thing Section 3 promised.

Memory trick — the form timeline

SAPscript → Smart Forms → Adobe: remember “Old Script, Smart middle, Adobe today.” If a question asks for the S/4HANA standard for output forms — answer Adobe Forms (PDF).

12 Interfaces: BAPI, RFC and IDoc

Lesson 3's “interface” meant the screen between you and SAP. Here the same word means something bigger: how SAP talks to other systems — banks, web shops, payroll software. Three names carry almost all of it.

NameFull form / simple meaningTypical FI use
RFCRemote Function Call — the mechanism that lets one system call a function module in another system and get the result back, like a phone call between programs.Your reporting tool asks SAP, live, for today's balances.
BAPIBusiness Application Programming Interface — a standard, published function module with a guaranteed interface, representing a business action. SAP promises BAPIs stay stable across upgrades.BAPI_ACC_DOCUMENT_POST — an external system posts accounting documents into FI through this official door. Explore them in BAPI (BAPI Explorer).
IDocIntermediate Document — a structured message envelope of data sent between systems, stored and monitored (e.g. WE02 to display, BD87 to reprocess errors). Sending can wait — IDocs queue up if the other side is down.Vendor invoices arriving from a scanning system; payment data exchanged with another SAP system.
Analogy — phone call vs registered post

An RFC/BAPI call is a phone call: both sides are present, the answer comes immediately, and if nobody picks up, nothing was delivered. An IDoc is registered post: the envelope is written, stamped, tracked at every step, and delivered when the receiver is ready — with a full paper trail if something goes wrong. Synchronous (call) vs asynchronous (post) — that one distinction answers most exam questions on this topic.

Exam trap — BAPI is not a separate language

A BAPI is an ABAP function module with extra rules (standardised, stable, documented, usually RFC-enabled). “BAPI” appearing as a programming-language option is wrong. And remember from Lesson 3: interface has two meanings in SAP — user interface (screens) and system interface (data exchange). The exam expects you to know which one a question means from context.

13 Changing SAP safely: enhancements & Z-objects

Standard SAP cannot do everything. Companies add their own logic — but there is a right way and a dangerous way, and the exam tests the difference.

The Z rule: customer objects start with Z or Y

SAP reserves names beginning with Z and Y for customers. Standard SAP objects never start with Z — so ZFI_TRIAL_BALANCE instantly tells everyone “this is ours, SAP did not deliver it, and an upgrade will not overwrite it.” That is why our little program in Section 5 carries a Z. (Z se shuru honay wala naam = company ka apna banaya hua; SAP ka standard kabhi Z se shuru nahi hota.)

Three ways to add your own logic — from safest to riskiest

MethodSimple meaningUpgrade safety
Enhancement (BAdI / user exit / enhancement point)SAP deliberately leaves empty sockets in its standard code. You plug your own code into the socket — SAP's code itself is untouched. A BAdI (Business Add-In) is the modern, object-oriented socket; user exits and customer exits are the older forms (SMOD/CMOD). Find BAdIs in SE18, implement in SE19.Safest — survives upgrades; the recommended way.
Custom development (Z-programs)Your own brand-new objects alongside the standard — extra reports, forms, interfaces.Safe — standard untouched.
ModificationDirectly editing SAP's own standard code. SAP allows it with a registered key, but every upgrade must re-check and often re-do it.Riskiest — avoid whenever an enhancement exists.
Analogy — the power socket vs cutting the wall

An enhancement is plugging your lamp into a socket the builder provided — clean, removable, safe. A modification is cutting open the wall to splice your wire into the builder's wiring — it works, but every renovation (upgrade) becomes your problem. Good consultants always ask first: “Is there a socket (BAdI) for this?”

And how does any of this reach Production? The transport (recap + one new detail)

From Lesson 2 you know changes travel DEV → QAS → PRD inside a Transport Request. New detail: development changes create a Workbench request, while pure settings (customizing) create a Customizing request. ABAP programs, DDIC tables and BAdI implementations ride in Workbench requests. Release them in SE09/SE10, import and monitor the queue in STMS. Nothing — no program, no enhancement — is ever typed directly into PRD. Exam favourite

Exam trap — “clean core”

SAP's current guidance for S/4HANA Cloud is the clean core principle: keep the standard system as untouched as possible, use released APIs and enhancement points, so upgrades stay painless. If a question contrasts “modifying standard code” with “using a BAdI / released API”, the BAdI/API answer is the one SAP wants — especially for the Cloud Private Edition in your exam title.

14 Debugging for beginners: /h and breakpoints

Debugging = watching a program run step by step to find where it behaves unexpectedly. You will not fix code — but you will use this to find why a posting failed.

New terms — debugger, breakpoint

The Debugger is a tool that pauses a running program and lets you walk through it line by line, watching values change. A breakpoint is a marked line where the program must stop and hand control to you — like a bookmark that halts the story at exactly that page.

The two moves every FI consultant knows

  1. Type /h in the command field (Lesson 3's command field!) and press Enter — SAP answers “Debugging switched on”. Now press the button that triggers the action (e.g. Post in FB50): instead of completing, SAP jumps into the Debugger at the first line of the posting program.
  2. Step and watch: F5 = step into (go one line deeper), F6 = step over (run this line, show me the next), F7 = step out, F8 = continue running until the next breakpoint. On the side you watch variables — e.g. the posting date or the period — and the moment a wrong value appears, you have found your culprit: usually a setting, not a code bug.
ABAP Debugger — paused in the posting program — illustration, not a real SAP screenshot
Program: SAPMF05A   Line: 1 482   Breakpoint reached
> IF bkpf-budat < gv_open_from. " posting date before open period?

Read the illustration: the program stopped because the posting date (15 Oct 2026) is before the first open date (1 Nov 2026) — the next line would throw the “closed period” error you met in Lesson 3. Diagnosis in ten seconds: the period is closed; the fix is in the posting-period settings, not in code. That is debugging earning its keep for a functional consultant. (Debugger aap ko wo exact line dikha deta hai jahan program ruka — aur aksar masla setting ka hota hai, code ka nahi.)

Exam / work trap

Debugging in Production is restricted and watched — it needs special authorisation, and you never change values there to “force” a posting. Debugging is for DEV/QAS diagnosis. Also remember its cousin from Section 5: if the program already crashed, you do not debug — you read the short dump in ST22.

15 ABAP on HANA: CDS views & code pushdown

The last concept — and the one that connects ABAP to S/4HANA itself. Two ideas only, both exam-relevant.

Idea 1: Code pushdown — do the heavy work where the data lives

In old systems, the pattern was: fetch millions of rows from the database to the application server, then total them in ABAP. HANA is so fast at calculating that S/4HANA flips the pattern: push the calculation down into the database and bring back only the small result. This principle is called code pushdown (or “code-to-data”).

Analogy — the warehouse and the calculator

Old way: truck every box from the warehouse to your office, count them there, truck them back. Pushdown way: send one instruction — “count the boxes” — and the warehouse (HANA) replies with a single number. Same answer, a fraction of the traffic. ACDOCA can hold hundreds of millions of lines; pushdown is why reports on it still answer in seconds.

Idea 2: CDS views — the modern way to define “smart tables”

New term — CDS view (Core Data Services)

A CDS view is a definition, written in a special ABAP-side language, that tells HANA: “take these tables, join them, calculate these totals, and present the result as if it were one table.” The heavy work executes inside HANA (pushdown in action). SAP delivers thousands of CDS views in S/4HANA — Fiori reports and analytics read them, and the Virtual Data Model (VDM) is simply the organised family of these delivered views. You define and view them in ADT/Eclipse; in the GUI you can display them in SE11.

(CDS view = aik tayyar-shuda “smart window” jo kai tables ko jod kar, hisaab kar ke, aik table ki shakal mein natija deti hai — aur saara bhaari kaam HANA ke andar hota hai.)

  • What changed for ABAP in S/4HANA, in one breath: programs still written in ABAP and run on the application server — but database work is pushed down (CDS views, optimised Open SQL), and old habits (reading totals tables that no longer exist) had to be re-written for ACDOCA.
  • AMDP — one name to recognise only: ABAP Managed Database Procedures let developers write procedures that run entirely inside HANA for the heaviest calculations. You will hear the word in projects; the idea is just “pushdown, maximum level”.
Exam trap

CDS views do not store their own data — like DDIC views, they calculate the result at read time from the underlying tables. And pushdown does not mean “ABAP is dead” or “everything runs in the database”: screens, checks and process logic still run as ABAP on the application server. Only the heavy data work moved down.

17 Exam traps for Lesson 4

Eight traps, all from the wording games the exam plays with this topic.

  1. “ABAP is SAP's database.” No — ABAP is a programming language. The database in S/4HANA is HANA. Language ≠ database ≠ operating system.
  2. “The Data Dictionary stores the business data.” No — the DDIC stores definitions (metadata). The data lives in the database tables. Dictionary = the registry book, not the land itself.
  3. Domain vs data element swap. Domain = technical (type, length). Data element = meaning + labels. If an option gives the domain the field label, it is wrong.
  4. Internal table vs database table. An internal table exists only in memory while the program runs. It is not stored, not transported, and gone at program end.
  5. “BSEG was removed in S/4HANA.” False — BSEG still exists. ACDOCA became the central line-item table; several old totals/index tables became compatibility views.
  6. “A BAPI is a programming language / an interface technology like IDoc.” A BAPI is a standardised, RFC-enabled function module — ABAP underneath. IDoc is a message format; RFC is the calling mechanism. Three different layers.
  7. “To add logic, modify the standard program.” The SAP-correct answer is almost always the enhancement (BAdI / exit) — modification is the last resort and the enemy of the clean core.
  8. “ABAP programs are client-dependent, written separately per client.” No — Repository objects (programs, DDIC) are client-independent: written once in DEV, valid for all clients, moved by Workbench transports.

Every technical term of this lesson, one line each. Use it for revision before the exam.

ABAP Objects
The object-oriented part of ABAP, built around classes and objects.
ADT
ABAP Development Tools — editing ABAP in Eclipse on a PC, connected to the SAP system.
AMDP

BAdI

A marked line in code where the Debugger pauses the running program.
CDS view

Class
A template (blueprint) defining data and behaviour; an object is a live copy made from it.
Clean core
SAP's principle of keeping the standard system unmodified — use enhancements and released APIs so upgrades stay easy.
Code pushdown
Moving heavy calculations from the application server down into the HANA database.
Compiler
The translator that checks source code and converts it into executable form.
Data element
DDIC object giving a field its business meaning and screen labels; uses one domain.
Data Dictionary (DDIC)
The central register (SE11) defining all tables, fields and data types, once for the whole system.
Debugger
Tool that runs a program step by step (F5/F6/F7/F8) while you watch values; switched on with /h.
Domain
DDIC object defining only the technical shape of a value: data type and length.
Dynpro
Technical name of an SAP GUI screen inside a module pool program.
Enhancement
Customer logic plugged into SAP-provided points (BAdI, exits) without touching standard code.
Function module
A reusable, self-contained piece of ABAP code with defined inputs/outputs (SE37); grouped in function groups.
IDoc
Intermediate Document — a tracked, structured message envelope for data exchange between systems.
Internal table
A temporary list of rows in a program's memory; disappears when the program ends.
Kernel
The core engine of the application server (written in C/C++) on which the ABAP runtime runs.
Modification
Directly changing SAP's standard code — possible, but upgrade-risky; last resort.
Module pool
A screen-based ABAP program behind most transactions.
Open SQL
ABAP's database-independent way of reading/writing tables; translated by the runtime for the actual database.
Package
A container grouping related development objects for organisation and transport.
Repository
The central store of all development objects (programs, DDIC definitions); client-independent.
RFC
Remote Function Call — mechanism for calling a function module in another system and receiving the result.
Runtime
The part of the application server that executes compiled ABAP programs inside work processes.
Search help
DDIC definition behind the F4 value list of a field.
Short dump
The error report saved when a program crashes; read in ST22.
Source code
The human-readable text of a program as typed by the developer.
Structure
A field list with no stored data — a shape for carrying one record inside a program.
Transparent table
A DDIC table that exists 1:1 as a real database table (BKPF, BSEG, ACDOCA).

19 Summary — key points for C_TS4FI

If you remember nothing else from Lesson 4, remember these.

  • ABAP (Advanced Business Application Programming) is the programming language SAP is written in — a business-oriented 4GL that reads almost like English, with every statement ending in a full stop.
  • ABAP runs on the Application layer: source code → compiler → ABAP runtime in a work process; objects live in the client-independent Repository, above the C/C++ kernel.
  • The ABAP Workbench is the built-in toolbox: SE80 navigator, SE38 editor, SE11 dictionary, SE16N data browser, SE37 functions, SE24 classes, SE93 T-code links.
  • The Data Dictionary defines everything once: domain (technical shape) → data element (meaning + labels) → fields of transparent tables, plus structures, views and search helps.
  • FI data lives in tables an accountant can read: BKPF header, BSEG lines, ACDOCA the S/4HANA Universal Journal — keyed by BUKRS + BELNR + GJAHR. Check them yourself in SE16N.
  • Reading ABAP needs only a few words: DATA, SELECT, LOOP, IF, READ TABLE, CALL FUNCTION, COMMIT WORK — and the memory trio: database table (permanent) vs internal table (in memory) vs work area (one row).
  • Object family: reports, module pools (behind T-codes), function modules, classes; forms evolved SAPscript → Smart Forms → Adobe Forms.
  • Interfaces: RFC = the call mechanism, BAPI = standard published function (e.g. BAPI_ACC_DOCUMENT_POST), IDoc = tracked asynchronous message.
  • Change SAP the safe way: Z/Y namespace for your own objects, enhancements (BAdI) instead of modifications, everything moved by Workbench transports — the clean core principle.
  • /h switches on the Debugger (F5/F6/F7/F8); crashes are read as short dumps in ST22.
  • S/4HANA ABAP = code pushdown + CDS views: heavy calculation inside HANA, logic still in ABAP on the application server.
