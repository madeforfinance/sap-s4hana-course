01 Quick recap of Lesson 1

Thirty seconds of revision — this lesson stands on these five points.

  • ERP = one software, one database, for the whole company.
  • SAP is the world's leading ERP software; FICO = FI (Financial Accounting) + CO (Controlling) is its finance side.
  • Generations: R/3 (1992) → ECC (2004) → S/4HANA (2015).
  • S/4HANA runs only on the HANA database — an in-memory database, so reports are real-time.
  • You use SAP through two faces: the classic SAP GUI (with T-codes) and the modern browser-based Fiori.

One question Lesson 1 left open: when you type an entry in SAP GUI and press Enter, where does your entry actually go? Who does the calculation? Where is the data saved? That journey is called SAP's architecture — and it is this whole lesson. (Entry likhne ke baad woh jaati kahan hai? Yahi is lesson ka asal sawal hai.)

02 What does “Architecture” mean?

New word — Architecture

Architecture means the internal design or structure of something — how its parts are arranged and how they work together. A building's architecture is its plan: where the rooms, stairs and wiring are. A software's architecture is the same idea: which parts exist, what each part does, and how they talk to each other.

So “SAP Architecture” simply means: how is the SAP system built inside, and how do its parts work together when you use it? Nothing more scary than that.

Analogy — a restaurant

Think of SAP as a big restaurant with three areas:

  • The counter / dining area — where the customer sits, sees the menu and gives the order. This is what the user sees and touches.
  • The kitchen — where the chefs actually cook the order. The customer never enters, but all the real work happens here.
  • The store room (godown) — where all the raw material is kept safely, in an organised way, ready whenever the kitchen asks.

Keep this restaurant in mind. In the next section you will see that SAP has exactly these three parts — SAP calls them layers.

New word — Layer / Tier

A layer (also called a tier, pronounced “teer”) is one level or floor of the design. Like the floors of a building, each layer has its own job and only talks to the layer next to it. SAP's design has three layers, so it is called a three-tier architecture.

Memory trick — the “3” in R/3

Remember from Lesson 1: the old famous SAP was called R/3. The 3 stands for these three layers! (And the R stands for Real-time.) So the name R/3 itself is a summary of this lesson: Real-time, 3 tiers. S/4HANA kept the same three-tier design.

03 The three layers — the big picture

Here is the whole lesson in one picture. Read the diagram first, then the table below it.

LayerSimple meaningRestaurant partWhat lives here in SAP
1. Presentation layerThe screens you see and type onDining area / counterSAP GUI, Fiori in a browser, mobile apps
2. Application layerThe working brain — runs the programs, does every calculation and checkKitchenApplication server(s) running SAP programs written in ABAP
3. Database layerThe store where all data is kept permanentlyStore room / godownSAP HANA database and its tables

Why separate the work into three layers?

  • Many users, one system: hundreds of accountants can connect their screens (Layer 1) to the same application servers and the same database. Everyone shares the same live data — the ERP idea from Lesson 1.
  • Power where it is needed: heavy calculations happen on big, powerful server computers (Layer 2), not on each user's small PC.
  • Easy to grow: if the company grows, you add more application servers — like adding more chefs to the kitchen — without changing the screens or the database.
  • Safety: users never touch the database directly. Every request passes through the application layer, which checks permissions and rules first.
Memory trick — P-A-D

Remember the order top to bottom: Presentation → Application → Database = “PAD”. Or in Urdu style: “Pehle screen, Aakhir mein data” — first the screen, in the middle the application, last the database. In the exam, the three names in this order answer many questions.

04 Layer 1: Presentation layer — the face of SAP

The presentation layer is everything on your own device: your office PC, laptop, tablet or phone. Its only jobs are:

  • Show screens to you (forms, lists, reports).
  • Take what you type (amounts, account numbers, clicks) and send it to the application layer.
  • Show the result that comes back.

It does no accounting itself and stores no business data. If your laptop is switched off or replaced, nothing is lost — all data is safe in Layers 2 and 3. (Aap ka laptop sirf ek TV screen hai — asal film server par chalti hai.)

The two faces you already know

SAP GUI

A program installed on your PC. Classic SAP look: menus, a command box for T-codes, and the famous blue-and-grey screens. Most FI consultants still do daily work here. “GUI” = Graphical User Interface — simply, “the screen you use with mouse and keyboard”.

SAP Fiori

SAP opened in a web browser (Chrome, Edge…). No installation. Work is organised as apps shown as tiles on a home page called the Fiori Launchpad. Works on phones and tablets too. This is SAP's modern face and the main face of S/4HANA.

New word — Client (software meaning)

Careful — the word “client” has two different meanings in the SAP world, and Lesson 2 uses both:

1) In general computing, a client is the small program/device that asks for service — e.g. SAP GUI on your PC is a “client” of the server. The computer that gives the service is the server. This pair is called client–server.

2) Inside SAP, a Client (with capital C) is a separate environment inside one SAP system — Section 9 explains this in full. Do not mix the two meanings!

Exam trap

“Data is stored in the presentation layer” — wrong. The presentation layer only displays. Also: “Fiori replaced the GUI completely” — wrong. In S/4HANA both exist, and both connect to the same application layer and the same data.

05 Layer 2: Application layer — the brain of SAP

New word — Server

A server is a powerful computer that stays switched on all the time and “serves” many users at once. It is not a screen you sit at — it usually lives in a server room or in a cloud data centre. Your PC asks; the server works and answers.

The application layer is made of one or more application servers. This is where the actual SAP system runs:

  • All SAP programs run here — the posting program behind FB50, the payment program, every report.
  • All checks and calculations happen here: Is the period open? Do debits equal credits? Does this user have permission? Is this G/L account blocked?
  • It receives your request from Layer 1, works on it, reads or writes data in Layer 3, and sends the result back to your screen.
New word — ABAP (first mention)

SAP's own programming language is called ABAP (Advanced Business Application Programming). Almost all SAP programs in the application layer are written in ABAP. As an FI consultant you do not need to be a programmer — but you must know that ABAP programs are what run here. ABAP gets its own full lesson later (Lesson 4 of this course), so for now just remember: ABAP = the language SAP itself is written in, running in Layer 2.

Analogy — the kitchen and its chefs

The application server is the restaurant's kitchen. One kitchen can have several chefs working in parallel — in SAP these parallel workers are called work processes (Section 8). A small company may run everything on one application server; a big company uses many application servers sharing the load, all cooking from the same store room (one database).

One system can have many application servers

This is a favourite exam point. The database is normally one per system, but application servers can be many. When you log on, a special service sends you to an application server that is free — you usually never notice which one. The list of application servers of a system can be seen with T-code SM51.

Memory trick

“Brain in the middle.” Whenever a question asks where something is calculated, checked, or executed in SAP — the answer is almost always the application layer. Screens only show; the database only stores; the application layer thinks.

06 Layer 3: Database layer — the memory of SAP

The database layer is where everything is stored permanently: every document you post, every customer and vendor, every G/L account balance. Switch the servers off and on again — the data is still there.

New word — Table

A database stores data in tables — like Excel sheets: rows and columns. One row = one record (for example, one document header). One column = one field (for example, posting date, amount, company code). When consultants say “the data is in table BKPF”, they mean: the document headers are stored in that table, the way one sheet in a workbook holds one list.

Tables an FI person will meet again and again

TableWhat it stores (simple words)
BKPFDocument headers — the top part of every accounting document: number, date, type, who posted it.
BSEGDocument line items — the individual debit/credit lines inside each document.
ACDOCAThe Universal Journal of S/4HANA — FI and CO line items together in one table (from Lesson 1).
SKA1 / SKB1The chart of accounts and company-code data of G/L accounts.
LFA1 / KNA1Vendor master data (LFA1) and customer master data (KNA1) — in S/4HANA these live under the Business Partner concept.

You do not need to memorise tables today. Just understand the idea: when you post in SAP, rows are written into tables like these, and every report simply reads those tables back.

Why HANA makes this layer special

From Lesson 1: in S/4HANA this layer is always the SAP HANA database. Two facts matter for the exam:

  • In-memory: HANA keeps the working data in fast memory (RAM), not only on slow disks — so reports that took minutes in ECC come back in seconds.
  • Column store: HANA stores tables mainly column by column (not only row by row), which makes adding up one column — like “total of the Amount column” — extremely fast. Perfect for accounting totals.
Analogy — godown vs ready shelf

A normal (disk) database is like fetching stock from a far godown every single time — safe, but slow. HANA is like keeping the stock on shelves inside the kitchen itself (in memory), neatly arranged by item type (columns). Cooking — sorry, reporting — becomes very fast.

Exam trap

S/4HANA can run on Oracle / SQL Server / DB2 — wrong. That freedom belonged to ECC. S/4HANA runs only on SAP HANA. This single fact appears in the exam again and again.

07 One posting, step by step — the full journey

Now put the three layers together. Watch one real FI action travel through the system.

Scene: You are the accountant. You open T-code FB50 (Post G/L Account Document — you will use it hands-on in a later lesson), type a simple entry — Debit Rent Expense Rs 50,000, Credit Bank Rs 50,000 — and press Save (Post).

The journey in words

  • Step 1 — Request: You press Post. The presentation layer (GUI/Fiori) sends your typed data over the network to an application server.
  • Step 2 — Checking & processing: A work process on the application server runs the posting program. It checks: debits = credits? Is the posting period open? Is the account valid for this company code? Do you have authorisation? If anything fails, you get an error message and nothing is saved.
  • Step 3 — Saving: All checks pass → the program writes the document into the database tables (header in BKPF, lines in BSEG, journal lines in ACDOCA) and takes the next document number.
  • Step 4 — Result: The application server sends back “Document … was posted”, and your screen simply displays it.
New word — Transaction (two meanings, again!)

1) A transaction in SAP everyday speech = a task/screen you open with a T-code, e.g. “the FB50 transaction”.
2) In database language, a transaction = one complete unit of work that either saves fully or not at all. Your posting above is one database transaction: either the whole document is saved, or nothing is. SAP never saves half a document — accountants call this same idea “a journal entry must balance before it is posted”.

Analogy — ordering food for delivery

You (screen) place an order on the app → the restaurant kitchen (application server) checks the items and cooks → ingredients come from the store (database) and the finished record is kept → the app shows you “Order delivered”. You never entered the kitchen or the store yourself. That is exactly how SAP works.

08 Inside the application server — Dispatcher & Work Processes

A little deeper — this part is small, but the exam loves two words from here: Dispatcher and Work Process.

One application server may receive requests from 200 users at the same moment. Who decides which request is handled first? And who does the handling?

New word — Dispatcher

The Dispatcher is the receptionist / traffic controller of an application server. Every incoming request first reaches the Dispatcher, which keeps a waiting line (queue) and hands each request to a free work process. When the work is done, the Dispatcher sends the result back to the user's screen.

New word — Work Process

A work process is a worker inside the application server that actually executes one request at a time — runs the program, talks to the database, prepares the next screen. An application server has several work processes of different types, working in parallel.

The five types of work processes

TypeSimple meaningEveryday example
Dialog (DIA)Handles your live, step-by-step screen workYou typing and posting in FB50, pressing Enter again and again
Background (BGD)Runs long jobs quietly, without a user waiting at the screenDepreciation run or a big report scheduled at night
Update (UPD)Writes the final changes into the databaseThe moment your checked document is actually saved
Enqueue (ENQ)The lock manager — stops two users from changing the same data at the same time“Vendor 1000 is locked by user AHMED” message
Spool (SPO)Handles printingPrinting a payment advice or a report

As an FI user you will mostly live in Dialog work processes, schedule month-end jobs in Background, and meet Enqueue whenever SAP says a record is “locked by another user”. That locked message is not an error in your entry — it simply means a colleague is editing the same vendor/document right now. Wait and retry.

T-codes that show this layer Good to know

T-codeWhat it shows
SM50Work processes of your application server — which are busy, which are free, what they are running.
SM66Work processes of all application servers together (global view).
SM51The list of application servers in this system.
SM04Users currently logged on to your application server.
SM12Lock entries — who has locked what (the Enqueue list).
SM37Background jobs — see and check jobs that run in the background.
Analogy — bank branch

The Dispatcher is the token machine + guard at a bank branch: you take a token and wait your turn. The work processes are the counter staff: some counters serve walk-in customers (Dialog), one desk processes files dropped off for later collection (Background), one officer finally stamps and files the papers (Update), one keeps the “file is with me” register so two officers never edit the same file (Enqueue), and one handles the printer (Spool).

Memory trick — “D-B-U-E-S”

Work processes: Dialog, Background, Update, Enqueue, Spool. Remember the sentence: “Daily Background Updates Ensure Smooth-printing.” Five types, one line.

09 What is a Client? — the deep dive Exam favourite

You met this word in Lesson 1. Now we finish it properly, because it sits right in the middle of SAP architecture — and in the middle of many exam questions.

New word — Client (SAP meaning)

A Client is a separate, self-contained environment inside one SAP system. It has its own set of business data, its own users, and its own settings that belong only to it. A Client is identified by a 3-digit number, from 000 to 999, which you type on the logon screen before your user name and password.

One installed SAP system (one database, one set of application servers) can hold several Clients side by side. They share the same programs and the same database software, but their business data is kept strictly separate — data of Client 100 can never be seen from Client 200.

Analogy — flats in one building

An SAP system is one apartment building. A Client is one flat inside it. All flats share the building's structure, lift and wiring (the programs), but each flat has its own furniture, its own family and its own lock (its data and users). The family in Flat 100 cannot open Flat 200's door or see its furniture.

The special clients SAP itself delivers

ClientWhat it is
000The reference client delivered by SAP with standard settings. Used as the clean starting copy for making new clients. Normal users do not work here daily.
001Another SAP-delivered copy of the reference client (historically the “example” client). Also not a working client.
066Reserved for SAP's own remote support service (EarlyWatch). You will likely never log on here.
e.g. 100, 200, 800Your company's own clients — created by copying the reference client, then used for configuration, testing, training or live work. Numbers are chosen by the company.

Why does one system need several Clients?

  • Safe practice: new staff can learn and make mistakes in a training client — live data is untouched.
  • Clean testing: new settings are tested in one client before they are allowed anywhere near real work.
  • Separate companies/groups: sometimes different purposes (e.g. a demo company) are kept as different clients in the same system.
Exam trap — the No. 1 trap of this lesson

In SAP, Client ≠ customer. A customer who buys your goods is a Customer / Business Partner. A Client is an environment inside the system. If an exam option says “the client placed an order”, read carefully which meaning is intended — in architecture questions it is always the environment.

Memory trick

Client = “Computer ke andar ka Ilaqa” — a separate area inside the computer system. And remember the number: a Client is always 3 digits. If you see a 3-digit number on a logon screen, it is the Client.

10 Client-dependent vs client-independent data

One step deeper — a small idea with a big exam value.

Almost everything in SAP belongs to one Client only. But a few things are shared by all Clients of the system. SAP has two exact words for this:

TypeMeaningExamples
Client-dependentBelongs to one Client only. Change it in Client 100, Client 200 does not see it.All business data (documents, vendors, customers), most FI configuration — company code settings, chart of accounts assignments, posting period settings.
Client-independent
(cross-client)		Belongs to the whole system. Change it once, it changes for every Client.ABAP programs themselves, and some general settings — e.g. the list of currencies and countries used by the whole system.
Analogy — flats again

Furniture inside your flat is client-dependent — only your flat has it. The building's lift, main gate and water tank are client-independent — repair the lift once, and every flat benefits. Programs are like the lift: one program, used by all clients.

Why should an FI consultant care? Because most of your future configuration (SPRO settings for FI) is client-dependent. You will set it in the configuration client, and it will not automatically appear in other clients or systems — it must be carried there by a Transport Request (Section 13). Keep this chain in mind; it explains half of how SAP projects work.

Exam trap

“All configuration in SAP is client-independent” — wrong. Most customising is client-dependent. And “programs are stored separately in each client” — wrong. ABAP programs are client-independent: one copy serves all clients.

11 System ID (SID) and Instance — two small names

When technical people talk, two short words keep coming up. Learn them now and you will never feel lost in a project meeting.

New word — SID (System ID)

Every SAP system has a short name of 3 characters called its SID (System IDentifier) — for example DEV, QAS, PRD, or any 3-letter/number code a company chooses, like S4P. The SID is the system's identity card: “Which system are you logged into?” — “PRD.” One SID = one system = one database.

New word — Instance

An instance is one running copy of the SAP application software on one server — practically: one application server, running, with its own Dispatcher and work processes. A system with 3 application servers has 3 instances (usually one main “central” instance plus additional “dialog” instances), all serving the same system and the same database.

WordOne-line meaningAnalogy
System (SID)One complete SAP installation: application servers + one databaseOne whole restaurant branch
InstanceOne running application server within that systemOne kitchen counter team inside the branch
ClientA separate environment inside the systemA separate, locked section of the branch for one party/event
Memory trick — “3 and 3”

SID = 3 characters (PRD). Client = 3 digits (100). On the logon screen you give both: the system (chosen in your SAP Logon list) and the Client number. Two 3s — easy to remember together.

12 The system landscape: DEV → QAS → PRD Exam favourite

New word — Landscape

A company's complete set of SAP systems, arranged in a line, is called its landscape. The standard landscape has three systems. Work flows through them in one fixed direction — never backwards.

SystemFull nameWhat happens here
DEVDevelopmentConsultants build configuration here (in its customising client) and developers write/change programs. Unit testing — quick self-checks — also happens here. No real business is run on DEV.
QASQuality AssuranceThe built settings arrive here and are tested properly with realistic data, often by business users. Training is also frequently done on QAS. If a test fails, the fix is made back in DEV — never directly in QAS.
PRDProductionThe live system where the whole company actually works — real invoices, real payments, real closing. Configuration is never created directly in PRD; it only arrives, tested, from QAS.
Analogy — a tailor's three rooms

DEV is the cutting room — the suit is stitched here, mistakes are cheap. QAS is the trial room — the customer tries the suit, checks the fitting. PRD is the wedding day — the suit is worn for real; nobody stitches on the wedding day. SAP settings follow exactly this journey.

Exam traps
  • “Configuration is done directly in the Production system” — wrong, and in real life it is forbidden. PRD only receives tested transports.
  • “QAS is where programs are developed” — wrong. Development happens in DEV; QAS is for testing what DEV produced.
  • “DEV, QAS and PRD are clients of one system” — wrong. They are three separate systems (three SIDs, three databases). Each system has its own clients inside it.

13 Transport Requests — how settings travel

If settings are built in DEV, how do they reach QAS and PRD? They travel in a sealed packet called a Transport Request.

New word — Transport Request (TR)

A Transport Request is a numbered container in which SAP packs your configuration changes (or a developer's program changes) so they can be moved (imported) into another system — DEV → QAS → PRD — exactly as they were made, in the right order, with a record of who made them. Think of it as a sealed, numbered courier parcel for settings.

Two kinds of transport requests

TypeWhat it carries
Customizing requestConfiguration settings — the SPRO work of consultants like you (client-dependent settings). This is the type an FI consultant creates every day.
Workbench requestDevelopment objects — ABAP programs and other client-independent development work of programmers.

The journey of your setting, step by step

  • Step 1: In DEV, you open SPRO and change a setting. SAP asks: “Create or choose a Customizing request?” Your change is recorded inside that request — nothing has moved yet.
  • Step 2: When the work is finished and checked, you release the request (T-code SE09 / SE10 — the Transport Organizer). Releasing = sealing the parcel and handing it to the courier.
  • Step 3: The system team (Basis) imports the request into QAS, usually through the Transport Management System, T-code STMS. You test in QAS.
  • Step 4: Tests pass → the same request is imported into PRD. Your setting is now live for the whole company.
New word — Basis

Basis is the technical administration side of SAP — the team that installs systems, manages users' technical access, moves transports, takes backups and keeps the servers healthy. FI consultants do the accounting settings; Basis looks after the machine room. You will say “please ask Basis to import this TR” many times in your career.

Analogy — registered post

A transport request is like sending an important file by registered post: it is packed and sealed (recorded changes), given a tracking number (the TR number), signed for at each stop (DEV → QAS → PRD), and never opened or edited on the way. If the file is wrong, you do not edit the parcel in transit — you prepare a new parcel in DEV with the correction.

Exam trap

Business data (documents, invoices) is never transported — only configuration and programs travel by transport request. Live data stays in PRD where it was created. If an option says “transport the posted documents to QAS”, it is wrong.

15 Why architecture matters for an FI consultant

“I am an accounts person — why should I care about servers?” Fair question. Here is the honest answer.

  • Your daily settings live in this structure. From Lesson 5 onwards you will configure company codes, fiscal years and charts of accounts in SPRO — in the DEV customising client — and your work will travel by transport to QAS and PRD. If you do not understand Clients and transports, you cannot do a consultant's job.
  • It explains everyday mysteries. “I created the vendor but the tester cannot see it” (different client/system). “The report is slow today” (application server load — check SM50/SM66). “Record locked by user…” (Enqueue — SM12). Architecture turns panic into a checklist.
  • The exam asks it directly. This lesson sits in the C_TS4FI topic “Overview and Deployment of SAP S/4HANA”. Client, landscape, and deployment questions are considered easy marks — if you have the concepts clear.
  • Deployment connects here too: remember the editions from Lesson 1 — On-Premise, Cloud Private Edition (your exam), Cloud Public Edition. “Deployment” simply means where Layers 2 and 3 physically run and who manages them: on the company's own servers (on-premise), or in a cloud data centre — dedicated to one company in Private Edition, shared and SAP-managed in Public Edition. The three layers themselves never change.
New word — Deployment

Deployment = the way the SAP system is installed and run: on whose computers, in which place, managed by whom. Same software, different “housing”. Your C_TS4FI exam is specifically about the Cloud Private Edition housing — one company's own S/4HANA system, hosted in the cloud, with the full flexibility of configuration and transports you are learning in this lesson.

16 Exam traps for Lesson 2

Read these the night before the exam. Each one has caught real candidates.

Trap 1 — Client means customer

No. In architecture, a Client is an environment inside one system, identified by 3 digits. A customer is a Customer / Business Partner.

Trap 2 — DEV / QAS / PRD are clients

No. They are three separate systems (SIDs), each with its own database and its own clients inside.

Trap 3 — Data is stored on the user's PC

No. The presentation layer only displays. All data lives in the database layer; all processing happens in the application layer.

Trap 4 — One system = one application server

Not necessarily. A system has one database but can have many application servers (instances) sharing the work.

Trap 5 — Configuration is done in Production

Never. Configuration is built in DEV, tested in QAS, and only then transported to PRD.

Trap 6 — Everything is client-dependent

No. Business data and most customising are client-dependent, but ABAP programs are client-independent — one copy for all clients.

Trap 7 — Transports move business data

No. Transports move configuration (Customizing requests) and programs (Workbench requests). Posted documents never travel.

Trap 8 — S/4HANA can use any database

No. S/4HANA runs only on SAP HANA. “Any database” was ECC's freedom, and it ended with S/4HANA.

17 Lesson 2 glossary (A–Z)

Every technical word of this lesson, in one place. Use it for revision.

ABAP
SAP's own programming language. The SAP programs that run in the application layer are written in ABAP.
Application Layer
The middle layer of SAP's architecture — where programs run and all checks and calculations happen, on application servers.
Application Server
A powerful, always-on computer that runs the SAP application software and serves many users at once.
Architecture
The internal design of a system — its parts, their jobs, and how they work together.
Basis
The technical administration side of SAP: installations, transports, backups, system health. Also the team that does it.
Client
In SAP: a separate, self-contained environment inside one system, identified by a 3-digit number. Not a customer.
Client-dependent
Belonging to one Client only — e.g. business data and most FI configuration.
Client-independent
Shared by all Clients of a system — e.g. ABAP programs, the currency list. Also called cross-client.
Customizing Request
The transport request type that carries configuration (SPRO) settings from DEV to QAS to PRD.
Database Layer
The bottom layer — where all data is stored permanently. In S/4HANA, always the SAP HANA database.
Deployment
How and where the system is installed and run — on-premise, Cloud Private Edition, or Cloud Public Edition.
DEV
Development system — where configuration and programs are built.
Dispatcher
The traffic controller of an application server: receives requests, queues them, and gives them to free work processes.
Enqueue
The lock service/work process type that prevents two users from changing the same data at the same time.
Instance
One running application server within a system, with its own Dispatcher and work processes.
Landscape
A company's full set of SAP systems in order — classically DEV → QAS → PRD.
Layer / Tier
One level of the architecture with its own job. SAP has three: Presentation, Application, Database.
PRD
Production system — the live system where the company does its real work.
Presentation Layer
The top layer — the screens on the user's device (SAP GUI, Fiori). Displays and collects input; stores nothing.
QAS
Quality Assurance system — where transported settings are tested before going live.
Server
A powerful computer, always on, that provides services to many users (the “clients” in the computing sense).
SID
System ID — the 3-character name of one SAP system, e.g. PRD.
Table
The database's way of storing data: rows (records) and columns (fields), like an Excel sheet. E.g. BKPF, BSEG, ACDOCA.
Three-tier Architecture
SAP's design of three layers — Presentation, Application, Database. The “3” in the old name R/3.
Transport Request (TR)
A numbered, sealed container that carries configuration or program changes from one system to the next (DEV → QAS → PRD).
Work Process
A worker inside an application server that executes requests. Types: Dialog, Background, Update, Enqueue, Spool.
Workbench Request
The transport request type that carries development objects (ABAP programs and other cross-client work).

18 Summary — key points for C_TS4FI

  • Architecture = how SAP is built inside. SAP S/4HANA uses a three-tier architecture — the “3” in the old name R/3 (R = Real-time).
  • Layer 1 — Presentation: SAP GUI and Fiori on the user's device. Shows screens, takes input, stores nothing, calculates nothing.
  • Layer 2 — Application: application servers run the ABAP programs; every check and calculation happens here. One system can have many application servers.
  • Layer 3 — Database: all data stored permanently in tables — and in S/4HANA always in the SAP HANA in-memory database.
  • Inside an application server: the Dispatcher queues requests; work processes execute them — Dialog, Background, Update, Enqueue, Spool.
  • A Client is a separate environment inside one system, identified by 3 digits (000 = SAP reference client). Client ≠ customer.
  • Data and settings are mostly client-dependent; programs are client-independent (shared by all clients).
  • Every system has a SID (3 characters). An instance is one running application server of that system.
  • The standard landscape: build in DEV → test in QAS → work live in PRD. Configuration is never made directly in PRD.
  • Settings travel in Transport Requests: Customizing requests carry configuration; Workbench requests carry programs. Business data is never transported.
  • Useful T-codes of this lesson: SM50 / SM66 work processes, SM51 application servers, SM12 locks, SM37 background jobs, SE09/SE10 transport organizer, STMS transport management.
