01 Where Lesson 2 stopped — the final lesson’s three jobs

The course’s last working session. First, remember exactly where you stand — then see today’s three jobs.

In Part 2 · Lesson 2 you finished building the company’s financial backbone: every entry got a unique code, you created and configured a Posting Period Variant (OBBO), assigned it to the company code (OBBP), opened periods with OB52, assigned the retained earnings account (OB53) inside the equity series, and verified everything in the Chart of Accounts. The structure is complete and entries can now be posted into it, period by period.

But a structure that only accepts entries is half a system. The other half — the half managers, auditors and the exam all care about — is reading: getting answers back out. That is today’s lesson, and it has three jobs:

JobQuestion it answersMain tools
1 · Financial year reporting“Show me the whole year — Balance Sheet and Profit & Loss for company code PK01.”S_ALR_87012284 · OB58
2 · Line item checking & document tracking“Show me every single entry inside this one account — and prove where this amount came from.”FBL3N · FB03
3 · Company code queries“Show me the raw data — entries under a specific G/L account, and the tax amounts, straight from the tables.”SE16N · S_ALR_87012357
Analogy · Godown se audit tak

Part 1 aur Part 2 ke pehle do lessons mein aap ne godown (warehouse) banaya — shelves (chart of accounts), darwaze ke timings (posting periods), aur munafa rakhne ki jagah (retained earnings). Aaj ka kaam stock check aur audit hai: poori inventory list nikalna (year report), kisi aik shelf ki har cheez ginna (line items), aur kisi aik cheez ka bill dhoond kar dikhana (document tracking).

Key term · Reporting

Reporting means reading the data that postings have stored and presenting it as an answer — a total, a list, a statement. A report never changes data; it only displays it. In SAP FI almost every report reads the same stored entries and simply slices them differently: by year, by account, by document, or by tax code. Report sirf dikhati hai, badalti nahi — jaise CCTV recording dekhna; recording mein kuch change nahi hota.

02 Reporting — turning stored entries into answers

Before touching any T-code, understand the one idea underneath all SAP FI reporting: totals are just line items, added up.

Every posting you make creates a document, and every document is made of line items — one row per account touched, with its debit or credit amount. In S/4HANA those line items are stored in one giant table, the Universal Journal (table ACDOCA), which you met in Part 1 · Lesson 9. Every report in this lesson is a different window onto that same table:

The three zoom levels Core idea

  • Totals level — the financial year report adds up thousands of line items and shows one number per account group: “Total fixed assets”, “Revenue for the year”. Fast, high-level, what management reads.
  • Line item level — FBL3N shows the individual rows inside one account: every posting, its date, document number and amount. This is where checking happens.
  • Document level — FB03 shows one complete document: all its lines together, who posted it, when, and its header details. This is the proof level.

The professional habit is to move down the zoom levels whenever a number looks wrong: total looks odd → open the account’s line items → find the suspicious row → open its document. Consultants call this drill-down: starting from a summary and digging, step by step, to the single entry that explains it.

Key term · Drill-down

Drill-down means double-clicking a summary figure to see the details underneath it. In SAP you can drill from a report total into the account’s line items, and from a line item into the original document. Jaise map par zoom karna — pehle poora sheher, phir gali, phir exact ghar.

Memory trick · Report = jawab, posting = sawal ka data

Posting data likhta hai, report usi data se jawab nikalti hai. Agar report ghalat lagay to pehle data (line items/documents) check karein — report khud kabhi data nahi banati.

03 The Financial Statement Version — skeleton of the Balance Sheet & P&L

The year report does not guess how to arrange your accounts. It follows a structure you define once: the Financial Statement Version.

A list of accounts in number order is not a Balance Sheet. A Balance Sheet has a shape: Assets on one side, Liabilities and Equity on the other, headings, subtotals, and the profit figure carried in from the P&L. In SAP that shape is an object called the Financial Statement Version (FSV).

Key term · Financial Statement Version (FSV)

A Financial Statement Version is a tree structure that decides which G/L accounts appear under which heading of the Balance Sheet and Profit & Loss statement, in which order, and where subtotals are calculated. It is defined with transaction OB58. The financial statement report simply walks this tree, adds up the accounts hanging on each branch, and prints the result. One company can keep several versions — for example one for local law and one for group reporting.

FSV aik darakht (tree) jaisi structure hai: konsa account kis heading ke neeche ayega. Report usi darakht ko parh kar Balance Sheet banati hai — account FSV mein nahi, to report mein bhi nahi.

How the tree is built

  • Nodes (headings) — text items like “Assets”, “Current Assets”, “Cash and Bank”. A node holds a subtotal of everything under it.
  • Account assignment — each node is given account ranges (for example 100000–119999 to “Cash and Bank”). Any account inside an assigned range appears under that node.
  • Debit / credit side — a node can be set to show accounts with debit balances, credit balances, or both, which is how the same account can land on the correct side of the Balance Sheet.
  • The P&L part — revenue and expense nodes feed the period’s profit or loss, which the Balance Sheet side then shows — connecting straight back to the retained earnings logic from Lesson 2.
Classic problem · “Accounts not assigned”

If an account was never covered by any range in the FSV, the report does not drop it silently — it collects such accounts in a special node usually called “Accounts not assigned”. If that node shows any balance, your Balance Sheet is structurally incomplete: the account exists and has postings, but the FSV tree has no branch for it. Fix = assign its range in OB58. Checking that this node is empty is the first verification step of every year-end report.

04 Step by step — running the financial year report

Now the hands-on part: produce the Balance Sheet and Profit & Loss for one full financial year for company code PK01.

Key term · Selection screen

Almost every SAP report opens with a selection screen: a form where you tell the report exactly what to include — which company code, which fiscal year, which periods. The report then reads only data matching your selection. Same report, different selection = different answer. Selection screen report se pehle ka “order form” hai — aap batate hain kya chahiye, report waisa hi jawab lati hai.

  1. Start transaction S_ALR_87012284 (classic menu name: Financial Statements; the classic transaction F.01 opens the same report).
  2. Enter the Company Code: PK01. (You may enter several company codes to combine them.)
  3. Enter the Chart of Accounts and the Financial Statement Version — for example PKFS from the previous section. Without an FSV, the report has no structure to follow.
  4. Enter the Reporting period: fiscal year (for example 2026) and periods 1 to 12 for the full year — or up to a single period for a month-end view. Add the special periods 13–16 only when year-end adjustments should be included.
  5. Optionally enter a Comparison period — the same periods of the previous year. The report then shows both years side by side with the difference, which is how “advanced” year reporting is normally presented to management.
  6. Press Execute (F8). The statement appears in FSV order: headings, subtotals, Balance Sheet result and P&L result.
  7. Verify before trusting it: scroll to the “Accounts not assigned” node — it must be empty — and check that the Balance Sheet balances (Assets = Liabilities + Equity including the period’s profit).
  8. Drill down on any figure that surprises you: double-clicking an account in the output takes you towards its line items — the bridge to the next job in this lesson.

Memory trick · Report ke 4 sawal

Har report chalane se pehle 4 cheezen check karein: Konsi company? Konsa saal? Konse periods? Konsi structure (FSV)? — Company, Year, Periods, Version. Galat jawab aksar ghalat report se nahi, ghalat selection se ata hai.

05 Line items — every entry, one row at a time

Totals tell you how much. Line items tell you why. This is the checking level of SAP FI.

A line item is a single row of a single document: one account, one amount, one debit/credit side, plus its posting date, document number, text and references. When an accountant says “check the account”, they almost always mean: open its line items and read them one by one.

Key term · Line item display & item status

Accounts whose master record has the “Line item display” switch on keep every individual row available for display. Each row also has a practical status for checking: an open item is not yet settled (for example an unpaid vendor invoice sitting in the payable account), a cleared item has been settled and linked to its clearing document (for example the payment that closed that invoice), and reports let you ask for open items, cleared items, or all items.

Open item = abhi hisaab baaki hai; cleared item = hisaab band ho gaya, payment se jud gaya. Line item checking matlab har row ko parh kar ye samajhna ke paisa aya kahan se, gaya kahan.

The three questions line items answer

  • Completeness — is every expected entry actually there? (The monthly rent posting is missing → the total is short by exactly one row.)
  • Correctness — is any entry there that should not be? (A duplicate posting shows up as two near-identical rows.)
  • Explanation — what makes up this balance? (The account total is simply the sum of these rows — no row, no amount.)
Analogy · Bank statement ki lines

Account ka balance aap ke bank balance jaisa hai — aik number. Line items usi account ki statement lines hain: tareekh, tafseel, amount. Balance par shak ho to aap number ko nahi, lines ko check karte hain. SAP mein bhi bilkul yehi tareeqa hai.

06 Step by step — FBL3N: entries under one G/L account

The single most-used checking screen in SAP FI. Learn it once; you will use it for G/L accounts, tax accounts and verification work everywhere.

Key term · FBL3N (G/L Account Line Items)

FBL3N displays the line items of one or more G/L accounts in one company code. Its sister transactions follow the same pattern: FBL1N for vendor line items and FBL5N for customer line items. In S/4HANA the Fiori-era equivalent for G/L is FAGLL03, but FBL3N remains the classic exam and workplace answer. Remember the family by the middle number: 1 = vendor, 3 = G/L, 5 = customer.

  1. Start transaction FBL3N.
  2. Enter the G/L Account — for example the rent expense account 510000 — and the Company Code PK01. (A range of accounts, or several accounts, can be entered.)
  3. Choose the item selection: Open items (with a key date), Cleared items (with a clearing period), or All items — for checking work, “All items” with a posting-date range is the usual choice.
  4. Set the Posting date range — for example the full financial year 01.01.2026 – 31.12.2026, or a single month when checking one period.
  5. Press Execute (F8). Every posting into that account inside your selection appears as one row: posting date, document number, document type, text, debit, credit, and the running balance.
  6. Use the list tools: sort by amount to spot duplicates, filter on a document type, and switch on subtotals (for example per period) from the layout menu.
  7. Compare the list total with the report total from Section 4. They must agree — the report total is these rows added together.

FBL1N vendor (1 = supplier), FBL3N G/L (3 = darmiyan wala, general), FBL5N customer (5 = client). Teenon ki screen aur tareeqa aik jaisa hai — aik seekha, teenon aa gaye.

07 Reading the line item list — status, clearing & drilling in

A list of rows is only useful if you can read it like a story: what came in, what is settled, what is still hanging.

What each column is telling you

Column / signalMeaningChecking use
Status symbolOpen item vs cleared item indicatorFilter “open only” to see what is still unsettled at period end
Document numberThe unique number of the document this row belongs toYour drill-down key — double-click opens the document
Document typeSA (G/L posting), KR (vendor invoice), KZ (vendor payment), DR (customer invoice)…Filter by type to separate invoices from payments
Clearing document / dateFilled only when the item is cleared — the document that settled itJump from an invoice to its payment and back
Text / assignmentFree text and reference fields entered at postingOften the fastest way to spot duplicates or wrong-period entries

Clearing — the link between an entry and its settlement Exam favourite

Clearing is SAP’s way of saying “this open item is now settled”. When a vendor invoice (open item in the payable account) is paid, SAP does not delete the invoice row; it marks it cleared, stamps it with the clearing date and the clearing document number of the payment. The two rows now point at each other forever — that pointer is exactly what auditors follow.

Analogy · Udhaar ki copy par nishan

Kirana shop ki udhaar copy mein jab customer paisay de deta hai, dukaan-daar entry ko kaat nahi deta — us par “wapis mil gaye” ka nishan aur tareekh laga deta hai. SAP ka clearing bhi yehi hai: entry rehti hai, bas us par settlement ka nishan lag jata hai.

The drill-in move: place the cursor on any suspicious row and double-click. SAP leaves the list and opens that row’s complete document. You have just moved from zoom level 2 to zoom level 3 — which is the next section.

08 Document tracking — FB03 and following a document’s trail

Every amount in SAP can be traced back to one document. Document tracking is proving it, step by step.

Key term · Document key & FB03

A posted document is identified by exactly three things together: Document Number + Company Code + Fiscal Year. The same number can exist in another company code or another year — only the three together are unique. Transaction FB03 (Display Document) opens a document when you give it this key. Inside, the document header (table BKPF) holds the posting date, document type, who created it and when; the line items (table BSEG, mirrored in ACDOCA) hold the account rows. You met both tables in Part 1 · Lesson 4.

Document ki pehchan teen cheezon se hai: number + company code + saal. Jaise aik hi naam ke do log — pura pata (sheher + mohalla + ghar number) hi asal pehchan hai.

Tracking a document, start to finish

  1. Arrive with a clue — a document number from FBL3N, a total that looks wrong, or a question from an auditor (“what is this 250,000?”).
  2. Open it — double-click the row in FBL3N, or start FB03 and enter document number + company code + fiscal year.
  3. Read the whole document — not just your account’s row: every line, both sides. A document always balances (total debit = total credit), so the other lines explain where the amount came from or went to.
  4. Check the header — posting date (which period did it land in?), document type (what kind of business event?), entered-by user and entry date (who posted it, and when — a posting entered late for an earlier period is a classic finding).
  5. Follow the trail further — from the document, the menu leads to its related documents and clearing partners: the payment that cleared it, or the invoice a payment belongs to. If a document was reversed, its reversal document is shown — SAP never deletes a posted document; a wrong posting is cancelled by a reversal document (FB08), and both stay visible.

Memory trick · Document = saboot

Report number par behes ho to jawab hamesha document hai. “Document dikhao” — jo amount document se trace na ho, wo samjho abhi verify nahi hua.

09 Company code queries — asking tables directly with SE16N

Reports answer standard questions. When the question is unusual, consultants query the tables themselves — carefully, and read-only.

Key term · SE16N — General Table Display

SE16N opens any database table and lets you filter its rows with your own criteria: “all rows where company code = PK01”. This is a query — a direct question to the database, without a pre-built report. You first used it in Part 2 · Lesson 1 to verify company data in table T001. SE16N is for display and checking; changing table data directly is not normal consulting work and is heavily restricted in real systems.

Report aik tayyar-shuda jawab hai; query apna sawal khud banana hai. SE16N se aap table se seedha poochte hain: “PK01 ki saari entries dikhao.”

Notice the pattern from Part 1 · Lesson 7: a G/L account has two segments — the chart segment (SKA1, shared by all company codes using the chart) and the company code segment (SKB1, one row per company code). Asking SKA1 “which accounts does PK01 have?” is a classic beginner mistake — the company-code answer lives in SKB1.

Running a company code query, step by step

  1. Start SE16N, enter the table — for example SKB1 — and press Enter so the selection fields appear.
  2. Set your criteria: BUKRS (company code) = PK01. Add more filters to narrow down, for example a G/L account range in SAKNR.
  3. Set Maximum number of hits sensibly — a company code can hold thousands of rows; start narrow.
  4. Press Execute (F8). The matching rows appear as a list you can sort, filter further, and export.
  5. Verify against a report: the count and content of your query should agree with what FBL3N / the chart display shows. Query and report reading the same data and agreeing = your verification is complete.

10 Checking tax amounts — the tax accounts and the tax report

Tax is where checking matters most: the amounts you report to the tax authority must be provable, account by account, document by document.

When a posting carries tax — for example sales tax on an invoice — SAP does not bury the tax inside the expense or revenue amount. The tax portion is posted to its own tax G/L account: broadly, input tax (tax you paid on purchases, an asset-side account) and output tax (tax you charged on sales, a liability-side account). Which account and which percentage is decided by the tax code on the posting — you met tax codes as part of document posting in Part 1.

Key term · Tax code & the advance tax return report

A tax code is a short key (defined per country with FTXP) that carries the tax type and percentage — for example “output tax 18%”. Every tax line on a document stores its tax code, so SAP can later group all amounts by code. The standard report S_ALR_87012357 — Advance Return for Tax on Sales/Purchases — does exactly that grouping for a company code and period: per tax code, the base amount and the tax amount, ready to cross-check against the tax accounts.

Tax code har tax line par chipka hota hai, is liye SAP baad mein code ke hisaab se saare tax amounts ikatthe kar sakti hai — yehi tax return ki bunyad hai.

Two ways to check a tax amount — use both

Way 1 · The tax report (by tax code)

Run S_ALR_87012357 for company code PK01 and the period. Read it per tax code: base amount × rate = tax amount. Any code whose tax amount does not match its rate on the base is a finding.

Way 2 · The tax account (by line item)

Run FBL3N on the output tax account itself (in our example series, a 2xxxxx liability account) for the same period. The sum of its line items must equal the report’s tax amount for that code — and every row drills into its document with FB03.

When Way 1 and Way 2 agree, the tax figure is verified at two independent zoom levels. When they disagree, the line items show you exactly which documents carry tax without a matching code, or a code without a posting — the usual causes are a posting made with the wrong tax code, or a manual posting directly to the tax account (which is why tax accounts are normally blocked for direct manual posting).

Exam trap · Tax is checked by code AND by account

A favourite exam twist: “The tax report total is correct, so no further check is needed.” Wrong habit. The report groups by tax code; the G/L account groups by posting. A posting with a wrong code can still land in the right account, and a manual posting can land in the account with no code at all. Professional checking compares both views — that comparison is the skill this section teaches.

11 Variants & layouts — ask faster, export cleanly

You will run the same checks every month. SAP lets you save the question once and reuse it forever.

Key term · Selection variant & layout

A selection variant saves the filled-in selection screen of a report under a name — company code, year, accounts, options — so next month you call the variant instead of typing everything again. A layout (in list displays such as FBL3N) saves how the result looks: which columns, in which order, sorted and subtotalled how. Variants save the question; layouts save the answer’s shape.

Variant = sawal save kar liya; layout = jawab ki shakal save kar li. Agle mahine sirf variant chalein, kaam waisa ka waisa.

  • Save a selection variant: fill the selection screen → menu Goto → Variants → Save as Variant → give it a clear name (for example PK01_MONTH_END) → save. Next time: Goto → Variants → Get, pick it, adjust only the period, execute.
  • Save a layout in FBL3N: arrange columns, sorting and subtotals → Settings → Layout → Save. Set your favourite as the default so your checking view opens ready-made.
  • Export for working papers: list displays export to spreadsheet (List → Export → Spreadsheet) — the standard way to attach evidence to an audit file. Export the data; never edit figures outside SAP and present them as SAP’s.
  • Print / spool: reports can be printed or saved as a spool request for a fixed, unchangeable copy of what the report showed at that moment.
Memory trick · Variant = recipe card

Jaise ammi ki recipe card — har dafa andazay se nahi, card dekh kar waisa hi khana. Month-end checks bhi recipe card (variant) se hone chahiyein, taake har mahine bilkul aik jaisi checking ho, kuch bhoolay nahi.

12 Worked routine — one complete month-end check

Now put all three jobs together, in the order a consultant actually performs them at period end.

  1. Run the period report. S_ALR_87012284 for PK01, periods 1–3, FSV PKFS. Check: statement balances, “Accounts not assigned” is empty, and no heading moved strangely versus last period.
  2. Spot the odd figure. Rent expense for the quarter reads 1,000,000 — but 3 months × 250,000 should be 750,000. One extra month is hiding somewhere.
  3. Drop to line items. FBL3N on account 510000, all items, posting dates for the quarter. Thirteen rows appear instead of twelve — including two “Rent March” rows of 250,000 on the same day.
  4. Track the document. Double-click the second March row → FB03 shows document 100000918: same vendor, same text, same amount as document 100000901, entered by the same user on the same day. Duplicate confirmed with evidence, not guesswork.
  5. Check the tax side. S_ALR_87012357 for the quarter, then FBL3N on the output tax account: totals agree per tax code — the tax figures need no correction.
  6. Query to be thorough. SE16N on T001B confirms which periods stand open (1–3 open for normal postings; the correction will land in the still-open period), and on SKB1 that account 510000 belongs to PK01 as expected.
  7. Conclude like a consultant. The duplicate is corrected by reversing document 100000918 (FB08) — never by deleting or editing it — and the report is re-run to show the corrected 750,000. Every step used only display and checking tools from this lesson, plus the reversal rule from document tracking.
Analogy · Doctor ki tarah jaanch

Pehle general check-up (report), phir jahan dard ho wahan detailed test (line items), phir report file khol kar saboot (document). Consultant ki checking bhi isi tartib se hoti hai — kabhi seedha andazay se operation nahi.

13 Exam traps

The mistakes this lesson’s exam questions are designed to catch. Read each one slowly.

Trap 1 · “The report total is wrong, so fix the report”

Reports calculate from line items; they hold no data of their own. A wrong total means a wrong or missing posting — you find it in FBL3N and prove it in FB03. You never “correct” a report.

Trap 2 · Account missing from the Balance Sheet

The account exists and has a balance, yet it does not appear under any heading. Cause: its number range is not assigned in the Financial Statement Version (OB58) — it is sitting in “Accounts not assigned”. The fix is in the FSV, not in the account.

Trap 3 · FBL1N / FBL3N / FBL5N mix-up

1 = vendors, 3 = G/L accounts, 5 = customers. Questions love swapping them. If the question says “G/L account line items”, the answer is FBL3N (S/4HANA also offers FAGLL03 for the same purpose).

Trap 4 · Document number alone is “unique”

It is not. A document is unique only as number + company code + fiscal year. FB03 always asks for all three — an exam option that identifies a document by number alone is incomplete.

Trap 5 · SKA1 vs SKB1

“Which accounts are created for company code PK01?” → SKB1 (company code segment). SKA1 is the chart segment and knows nothing about which company code uses the account.

Trap 6 · Cleared means deleted

Clearing never deletes anything. A cleared item stays fully visible, stamped with its clearing document and date. Deleting posted documents is not possible at all — correction happens by reversal.

Trap 7 · Checking tax in only one view

The tax report (S_ALR_87012357) groups by tax code; FBL3N on the tax account groups by posting. Either view alone can hide an error the other one catches. The exam’s “best practice” answer is to reconcile both.

15 Summary — the whole lesson on one screen

If you remember this one section, you remember the lesson.

  • All FI reporting reads one source: the line items of the Universal Journal (ACDOCA). Reports only slice them differently.
  • Three zoom levels: year report (totals) → FBL3N (one account’s line items) → FB03 (one document). Checking always moves downwards.
  • The Balance Sheet / P&L report (S_ALR_87012284 / F.01) follows the Financial Statement Version (OB58). First verification: “Accounts not assigned” must be empty and the statement must balance.
  • FBL3N checks entries under a specific G/L account — open, cleared or all items, by posting-date range. Family: FBL1N vendors, FBL5N customers.
  • Clearing links an item to its settlement; cleared items stay visible with clearing document and date. Nothing posted is ever deleted — errors are reversed.
  • A document is unique by number + company code + fiscal year; FB03 shows header (BKPF) and lines (BSEG/ACDOCA) — the proof level of every amount.
  • Company code queries with SE16N ask tables directly: T001 company codes, SKB1 accounts per company code, SKA1 accounts per chart, T001B open periods.
  • Tax checking uses two views: S_ALR_87012357 groups tax amounts by tax code; FBL3N on the tax account groups them by posting. Both must agree.
  • Variants save the question, layouts save the answer’s shape — the professional way to repeat month-end checks identically.
