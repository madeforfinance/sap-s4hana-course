Analogy · Setting up a new shop’s cash register

Before the first sale, a shopkeeper does three things. One: he decides the till counts in rupees — and pins a small rate card next to it: “$1 = Rs 278” for the day a tourist pays in dollars. Almost everything in this lesson is about preparing these accounts and the rules around them.

02 Currency in SAP — one posting, several amounts

Video 03:57:35 — first the accounting idea, then the SAP settings.

Take a posting you already understand. Your Pakistani company buys fabric from a US supplier for USD 1,000. In your manual books (kept in rupees) you would write one line: Purchases Dr — Rs 278,000 (at today’s rate of 278). One amount, one currency — simple.

SAP is more careful. It stores the same posting in several currencies at the same time, because different readers need different views of the same truth:

New term · Transaction Currency (Document Currency)

The transaction currency is the currency of the business deal itself — the currency printed on the invoice. Here: USD, because the supplier billed in dollars. SAP also calls it the document currency, and its technical field is WAERS in the document header. Amount in transaction currency: WRBTR.

New term · Local Currency (Company Code Currency)

The local currency is the currency of the company code’s legal books — the currency of its official Balance Sheet and tax filings. For a Pakistani company code: PKR. Every posting is always translated into local currency; this is the amount your statutory (legal) reports use. Amount in local currency: DMBTR.

Local currency woh hai jisme company ki official, qanooni books banti hain. Pakistan ki company code ki local currency PKR hogi — ye badli nahi ja sakti aasani se.

New term · Parallel Currency

A parallel currency is an additional currency in which SAP values every posting at the same time as the local currency — for example the group currency (the parent company’s currency, say EUR) so the head office can consolidate (combine) all companies without translating later. Section 4 explains the types.

Memory trick

Invoice ki currency = transaction. Books ki currency = local. Boss ki currency = group. The invoice decides the first, the law decides the second, the head office decides the third.

03 Currency keys, ISO codes & decimals (OY03)

How SAP names currencies — and one small setting that causes big confusion if ignored.

SAP never writes the word “rupees” in its tables. Every currency is stored as a short currency key — almost always the international ISO code.

New term · Currency Key & ISO Code

A currency key is the 3-letter code that identifies a currency everywhere in SAP: PKR (Pakistani rupee), USD (US dollar), EUR (euro), AED (UAE dirham), JPY (Japanese yen). SAP follows the ISO 4217 standard — the same codes you see at airports and money changers. The list of allowed currencies is checked in transaction OY03 (SPRO → SAP NetWeaver → General Settings → Currencies → Check Currency Codes) and stored in table TCURC.

The decimal-places trap

Most currencies divide into 100 small units (1 rupee = 100 paisa), so SAP stores amounts with 2 decimals. But not all currencies work that way:

CurrencySmall unitsDecimals in SAPWhat USD 100 looks like stored
USD, PKR, EUR100 (cents / paisa)2100.00
JPY (yen)None — no “cents”0100 (never 100.00)
KWD (Kuwaiti dinar)1,000 fils3100.000

These exceptions are maintained in table TCURX (SPRO → Currencies → Set Decimal Places for Currencies). SAP stores all amounts internally as if they had 2 decimals, and uses TCURX to shift the decimal point when displaying or converting. That is why a yen amount entered carelessly can suddenly become 100 times too big or too small.

Exam trap preview

“An amount in JPY appears 100 times larger after conversion.” The cause is almost always the decimal places setting (TCURX), not the exchange rate. Remember: rates translate value; decimals place the point.

The currency checklist in SPRO

  • Check currency codes — OY03 · table TCURC — which currencies exist at all.
  • Check exchange rate types — OB07 · table TCURV — which kinds of rate exist (Section 5).
  • Define translation ratios — OBBS · table TCURF — the units a rate is quoted in (Section 5).
  • Enter exchange rates — OB08 · table TCURR — the actual daily rates (Section 5).
  • Set decimal places — table TCURX — the exceptions like JPY and KWD above.

Ye paanch settings mil kar “currency settings” banti hain. In mein se roz ka kaam sirf OB08 hai — baaki aam tor par aik dafa set hoti hain.

04 The company code currency & parallel currencies (OB22)

Where the local currency was set (back in Lesson 5), and how extra parallel currencies are switched on.

The local currency — decided once, at birth

You already met this setting without noticing its importance: when the company code was defined in OX02 (Lesson 5), one field fixed its currency — Currency, stored as T001-WAERS. That single field is the company code’s local currency. Every document posted in that company code is translated into it, every legal report reads it, and the trial balance balances in it.

Exam trap preview

The company code currency cannot simply be changed later. Once documents exist, changing WAERS would rewrite history — SAP treats the local currency as a decision you make before the first posting. In an exam scenario, “the consultant wants to change the company code currency after go-live” is a red flag answer.

Parallel currencies — up to two more views of the same books

Classic SAP company codes can carry, in addition to the local currency, two more currencies in which every posting is also valued — maintained in transaction OB22 (Define Additional Local Currencies). Each parallel currency has a currency type — a code that states why this extra view exists:

Currency typeNameWhy it exists — in simple words
10Company code currencyThe local currency itself (the legal books).
30Group currencyThe parent company’s currency. All subsidiaries keep a parallel copy of every amount in it, so group consolidation (Lesson 5’s Company) needs no later translation.
40Hard currencyA stable foreign currency (usually USD) used by companies in countries with high inflation, where the local currency’s value melts too fast to trust for reporting.
50Index-based currencyA currency used in inflation-index reporting required by law in some countries.
60Global company currencyA currency defined for a Company (the consolidation unit from Lesson 5) — like group currency, but attached to the company rather than the whole group.
New term · Ledger

You will need one more word soon. A ledger in SAP is a complete set of books kept under one set of accounting rules — for example your leading ledger 0L holds the official books. Parallel currencies are configured per ledger in S/4HANA, because different rule-sets may need different currency views. The full Ledger lesson comes later in this course; for today, just remember: ledger = one full set of books.

Analogy · One match, three scoreboards

A cricket match is one event. But the stadium scoreboard shows runs, the TV shows runs and required rate, and the radio describes it in another language — all live, all from the same balls bowled. Parallel currencies are the same: one posting, shown live in local, group and hard currency. Nobody re-plays the match to get the other scoreboard.

S/4HANA note S/4HANA favourite

In S/4HANA the Universal Journal (table ACDOCA — full lesson later) can store many currency amounts per line: the transaction currency, the company code currency, and additional parallel / freely defined currencies per ledger. The beginner-level truth stays the same: the company code currency is always there; every extra currency must be deliberately switched on in Customizing (OB22 / ledger settings) before postings begin — you cannot add a parallel currency later and expect old postings to have values in it.

05 Exchange rates — types, quotations & the rate table (OB07 · OB08)

The rate card pinned next to the till — SAP’s version, with four moving parts.

New term · Exchange Rate

An exchange rate is the price of one currency in terms of another: “1 USD = 278 PKR”. SAP stores thousands of these — per currency pair, per rate type, per date — in table TCURR, and uses the rate valid on a document’s posting / translation date to convert its amounts.

Part 1 — Exchange rate types (OB07): one pair of currencies, several honest prices

A money changer does not have ONE rate for dollars. He buys your dollars cheap and sells you dollars expensive, and the newspaper prints a middle “average” rate. SAP copies this real-world idea with exchange rate types (table TCURV, checked in OB07):

Rate typeMeaningUsed for
MAverage rate (standard translation)The everyday rate for postings and most translations. When SAP asks “which rate type?”, the answer is almost always M.
BBank selling rateThe rate at which the bank sells foreign currency — used in some bank / payment processes.
GBank buying rateThe rate at which the bank buys foreign currency.

Each exchange rate type also carries two quiet but important settings: the reference currency (a base currency all rates can be derived through — often USD or EUR) and the flags for which quotation is standard (next part).

Part 2 — Direct vs indirect quotation

The same fact can be written two ways, and SAP supports both (you met this at any money changer):

  • Direct quotation — “How much local money for ONE unit of foreign?” → 1 USD = 278.00 PKR. The foreign unit is fixed at 1 (or 100), the local amount moves.
  • Indirect quotation — “How much foreign money for ONE unit of local?” → 1 PKR = 0.003597 USD. The local unit is fixed; the foreign amount moves.

In the rate table, indirect quotation is marked with a leading slash in the “from currency” — you will see it in the illustration below. A rate type defines which quotation is the standard for a currency pair, so users always enter rates the same way.

Part 3 — Translation ratios (OBBS): rates are quoted in units

New term · Translation Ratio

A translation ratio says in which units a rate between two currencies is quoted — for example 1 : 1 (1 USD = 278 PKR) or 100 : 1 for very small currencies whose 1-unit rate would be a long decimal. Ratios are defined per currency pair and rate type in OBBS (table TCURF) and are valid from a date — change the ratio, and you must enter new rates from that date.

Part 4 — Entering the rates themselves (OB08)

All of the above exists so that one simple daily job works: typing the day’s rates into OB08 (Enter Exchange Rates, table TCURR). Each row is: rate type + from-currency + valid-from date + rate + ratio + to-currency. In real companies these rows are often loaded automatically from a central-bank feed; the manual screen below is what the exam expects you to know.

Memory trick · The rate card’s four corners

Type (which price — M), Quotation (which way it is written), Ratio (in what units), Table (the rates themselves — OB08/TCURR). Exam questions attack one corner at a time; naming all four keeps you safe.

Exam trap preview

If no rate exists in TCURR for the posting date, SAP looks for the most recent older rate for that pair and type — it does not stop the world. But if there is no rate at all for the pair, the posting fails. And remember which type FI postings use by default: M, not B or G.

06 Worked example — a USD purchase in a PKR company code

All of Sections 2–5 happening inside one real posting.

Setup. Company code PK01 (Ibrahim Apparel & Trading, Pakistan): local currency PKR, one parallel currency — group currency EUR (type 30). Rates in TCURR for today, type M: USD → PKR 278.00; USD → EUR 0.92.

Event. A supplier invoice arrives: fabric, USD 1,000, dated today. The accountant posts it with FB60 (vendor invoice — full lesson later in this course):

FB60 — Enter Vendor Invoice (simplified) · re-created illustration, not a real SAP screenshot
Document header
Vendor      : US-SUPPLIER-01    Invoice date: 26.11.2026   Posting date: 26.11.2026
Currency     : USD (transaction currency — typed by the user)
Exch. rate   : 278.00 (proposed automatically from TCURR, type M — can be overwritten)

Line items — what SAP stores for the SAME document
Purchases (Dr)     : USD 1,000.00  | PKR 278,000.00  | EUR 920.00
Vendor payable (Cr) : USD 1,000.00  | PKR 278,000.00  | EUR 920.00

What just happened, step by step

  • 1. The user typed only USD 1,000 — the currency of the paper invoice.
  • 2. SAP read the posting date, went to TCURR, and proposed rate type M for USD→PKR: 278.00. (A user with authority may overwrite the proposed rate on the document; the document then remembers the rate actually used.)
  • 3. SAP translated: local amount PKR 278,000 — this is the amount the legal books, the trial balance and the tax reports will use.
  • 4. Because a group currency was switched on in OB22, SAP also translated into EUR 920 at the same moment — no extra work for the accountant, ever.
  • 5. All three amounts were saved on the document lines (in S/4HANA, in the Universal Journal ACDOCA). If the rate changes tomorrow, this document does not change — history keeps the rate of its own day. Later revaluation of open items is a separate, later topic.
Analogy · The money changer’s receipt

When you change dollars at the airport, the receipt shows three things: dollars given, rate applied, rupees received. SAP’s document is that receipt — with the group currency written on it too, for the head office. And just like the paper receipt, it is never reprinted when tomorrow’s rate changes.

07 Chart of Accounts — the master list of G/L accounts (OB13)

Video 04:18:47 — the second big topic. Again: accounting idea first, SAP setting second.

In your Financial Accounting studies you have already drawn this by hand many times: the list of every account a business uses — Cash, Bank, Capital, Purchases, Sales, Rent, Salaries, Electricity… — each with a number. Accountants call that list the chart of accounts. SAP uses exactly the same idea and the same name.

New term · Chart of Accounts (CoA)

A Chart of Accounts is the complete, organised list of all G/L accounts that a company (or group of companies) is allowed to post to. Every G/L account in SAP belongs to exactly one chart of accounts. The chart itself is defined once in transaction OB13, stored in table T004, and has a 4-character key — for example SAP’s well-known standard chart YCOA in S/4HANA (the classic example was INT). Its technical field name is KTOPL.

Chart of Accounts = tamam khaaton ki mukammal list. Jo khata is list mein nahi, us par entry nahi ho sakti — bilkul waise hi jaise register mein wohi safha khulta hai jo pehle se bana ho.

What is defined when you create a chart (OB13)?

  • Chart key & description — e.g. YCOA, “Standard Chart of Accounts”.
  • Length of the G/L account number — how many digits account numbers in this chart have: up to 10 digits. This is decided per chart, not per account — choose 6, and every account number in that chart is up to 6 digits.
  • Controlling integration — whether cost elements (CO view of expense accounts) are created manually or automatically. (CO is a later course topic; the field simply lives here.)
  • Group chart of accounts — an optional link to the group chart (Section 8).
  • Status — a chart can be blocked while it is still being built, so nobody posts to a half-finished list.
Analogy · The register’s index page

A paper ledger register starts with an index: page 1 Cash, page 2 Bank, page 3 Sales… The index itself holds no amounts — it only declares which accounts exist and where. The Chart of Accounts is SAP’s index page. Amounts live in the accounts; the chart only lists them.

Memory trick

OB13 = “Oh Bhai, 13 — list banao.” And the chart’s field name KTOPL reads like “Khaaton ki TOP List” — the top list of accounts. Silly, but it sticks.

08 Three kinds of chart — operating, group & country (OB62)

The part of the Chart of Accounts topic the exam loves most.

One chart serves daily work. But big organisations have two more needs: the head office wants every country’s numbers in ONE common list, and a local law sometimes demands accounts numbered in a government-prescribed way. SAP solves both without disturbing daily work — with three roles a chart can play:

Operating Chart of AccountsGroup Chart of AccountsCountry Chart of Accounts
PurposeDay-to-day postings — the chart the company code actually works withOne common list for the whole group, so all companies’ results can be combined and comparedA chart prescribed by a country’s law / tax authority
Assigned where?To the company code — OB62To the operating chart — in OB13To the company code — OB62 (as an additional assignment)
How many per company code?Exactly one— (via its operating chart)At most one, and optional
Link is stored…—In the group account number field of each G/L account (chart segment)In the alternative account number field of each G/L account (company code segment)

Three facts the exam builds questions on

  • Sharing: the same operating chart can be assigned to many company codes — even in different countries and different local currencies. One chart, many company codes is normal, not an error. (Remember the variant principle from Lesson 6: define once, assign many times.)
  • One only: a company code can have exactly one operating chart. There is no “second daily chart”.
  • No postings in group / country charts: nobody posts directly to group or country accounts. They exist only as mapping targets — reporting views reached through the group / alternative account number stored on each operating account.
New term · Assign Chart of Accounts to Company Code (OB62)

Transaction OB62 is where the operating chart (and optionally a country chart) is assigned to a company code — the same assignment is also visible in the company code’s global parameters (OBY6, Lesson 5). Until this assignment exists, the company code has no accounts and cannot post anything.

Analogy · One student, three roll numbers

A student has one name but three numbers: his class roll number (used daily — the operating account), his board examination number (used when results of all schools are combined — the group account number), and his CNIC-style national number (used for government records — the alternative / country account number). He is one person; the numbers are just different views for different readers. A G/L account is the same.

09 The G/L account master — two segments (FS00)

A chart is only a list of numbers until each account is created as master data. Here is how one account is built.

New term · Master Data & Segments

Master data is the standing data SAP reuses in every transaction — accounts, customers, vendors (compare Lesson 6: master data vs transaction data). A G/L account’s master record is built in two segments (parts), because some facts about an account are the same for the whole group, while others differ per company:

1 · Chart of Accounts Segment — table SKA1

Created once per chart (T-code FSP0). Holds what is true everywhere the chart is used:

  • Account number & name (texts in table SKAT)
  • Account group (Section 10)
  • P&L account or Balance Sheet account
  • Group account number — the link to the group chart (Section 8)

2 · Company Code Segment — table SKB1

Created once per company code that uses the account (T-code FSS0). Holds what may differ per company:

  • Account currency (which currency the account may be posted in)
  • Tax category, reconciliation account type
  • Field status group (Section 12 — remember this field!)
  • Alternative account number — the link to the country chart

Transaction FS00 — Edit G/L Account Centrally — maintains both segments on one screen, which is why consultants live in FS00 and the separate FSP0 / FSS0 are used mainly for mass work.

Exam trap preview

“The account exists in the chart but cannot be posted in company code PK01.” Classic cause: the company code segment (SKB1) was never created for PK01. An account is postable in a company code only when both segments exist. And the reverse: one chart segment can serve many company codes — you do not recreate the account name per company.

10 Account groups — number ranges & control (OBD4)

The last piece of the Chart of Accounts topic: how accounts are organised inside the chart.

New term · Account Group (G/L)

An account group is a category inside a chart of accounts — Assets, Liabilities, Revenue, Expenses, Cash & Bank… — defined per chart in transaction OBD4 (table T077S). Every G/L account must belong to one account group (you saw the field in the SKA1 segment above). The group does two jobs:

Job 1 — It controls the number range

Each group owns a number interval: for example Assets = 100000–199999, Revenue = 400000–499999. When you create a new account, SAP only accepts a number inside its group’s interval. This is why experienced accountants can “read” a number: a 4xxxxx account is revenue before they even see its name.

Job 2 — It controls the master-data screen

The account group also carries a field status for the account’s own master record: while creating an account of this group, which fields are required, optional or suppressed? Example: for a reconciliation account group, certain fields behave differently than for a normal expense account. Hold this thought — it is one half of the Field Status topic, and Section 11 separates the two halves carefully.

Example account groupTypical number rangeWhat it quietly enforces
ASST — Assets100000 – 199999Balance sheet accounts live here
LIAB — Liabilities & Equity200000 – 299999Capital, loans, payables control accounts
REVN — Revenue400000 – 499999P&L statement accounts
EXPN — Expenses500000 – 599999P&L statement accounts
CASH — Cash & Bank110000 – 119999Often its own group for tighter control
Analogy · Aisles in a warehouse

A warehouse does not throw goods anywhere: aisle 1 is grains, aisle 2 is oils. The aisle decides where a new item may be placed (number range) and what label it must carry (master-data fields). Account groups are the aisles of the chart of accounts — OBD4 is where you paint the aisle signs.

Creating a chart of accounts — the full recipe

  • Step 1 — Define the chart: OB13 — key, description, account-number length, optional group chart link.
  • Step 2 — Assign it: OB62 — operating chart (and optional country chart) to each company code.
  • Step 3 — Define account groups: OBD4 — groups with number intervals, per chart.
  • Step 4 — Create the accounts: FS00 — chart segment + company code segment for every account.
  • Step 5 — Unblock & post: remove the chart’s block (if set in OB13) once the list is complete.

11 Field Status — what it is and why it exists

Video 04:49:13 — the third topic. It answers a question every form-designer asks.

Picture the SAP posting screen for a journal entry (you will use FB50 soon). It has dozens of possible fields per line: account, amount, cost center, profit center, business area, text, assignment, tax code, payment terms, trading partner… No real posting needs all of them — and some postings desperately need a few of them. If the accountant forgets the cost center on a rent posting, CO reporting breaks. If the screen asks for a trading partner on a simple cash expense, it only wastes time.

Somebody must decide, field by field: compulsory, allowed, shown-but-locked, or invisible. That decision is the field status.

New term · Field Status

The field status of a field controls how that field behaves on a data-entry screen. Every field gets exactly one of four statuses:

StatusMeaning in simple wordsWhat the user sees
Required (Must fill)The posting cannot be saved while this field is emptyField shown, usually marked; error if left blank
Optional (May fill)Fill it if relevant, leave it if not — both are fineField shown, normal
Display (Show only)The value is shown but cannot be typed or changed — it was filled by the system or a defaultField shown, greyed out
Suppress (Hide)The field is not shown at all and can hold no value in this contextField invisible
Analogy · A printed admission form

A school admission form has boxes with a red star — student name, father’s name (Required). Some boxes have no star — hobbies (Optional). The office stamps the roll number itself — you may read it but not write it (Display). And the form for Class 1 has no previous board marks box at all (Suppress). Field status is exactly this printing decision — made once by the consultant, obeyed by every posting screen afterwards.

Critical distinction · Two different “field statuses”

Beginners mix up two settings that share the name. Keep them apart from today:

(A) Master-data field status — controls the screen where you create an account / customer / vendor. For G/L accounts it comes from the account group (OBD4, Section 10).

(B) Posting field status — controls the screen where you post a document (FB50, FB60…). It comes from the field status group of the G/L account combined with the posting key. Sections 12–13 are about (B).

12 Field Status in detail — variant, groups & posting keys (OBC4 · OBC5 · OB41)

The posting-side field status (B) has three moving parts. Learn them in order.

Part 1 — The Field Status Variant (OBC4 / OBC5)

New term · Field Status Variant

A field status variant is a named bundle of field status groups — another use of the Lesson 6 variant principle: define once, assign to many company codes. The variant is defined in OBC4 and assigned to each company code in OBC5 (it also appears in the company code’s global parameters, OBY6). SAP delivers a standard variant, commonly 1000, which most projects copy. Technical field: T001-FSTVA.

Part 2 — Field Status Groups (OBC4)

New term · Field Status Group

Inside the variant live field status groups — small rule-cards, one per kind of account. A group says, for every field on the posting screen, which of the four statuses it has. Each G/L account then carries one group in its company code segment (the SKB1 field you saw in FS00, Section 9). Groups are 4 characters; SAP delivers examples like G001 (general), G005 (cost accounts), G052 (reconciliation-type accounts) — projects usually create their own.

Why per account-kind? Because the right rules differ by account: postings to expense accounts should demand a cost center (Required); postings to the bank account should not even show one (Suppress); postings to a vendor reconciliation account need fields that a salary account never sees.

Part 3 — Posting Keys (OB41)

New term · Posting Key

A posting key is a 2-digit code that tells SAP what kind of line is being posted — debit or credit, and to what kind of account. You have actually been using their paper ancestors for years: 40 = debit to a G/L account, 50 = credit to a G/L account, 31 = credit to a vendor, 21 = debit to a vendor, 01 = debit to a customer, 11 = credit to a customer. Posting keys are maintained in OB41 (table TBSL) — and each posting key also carries its own field status, because a vendor line and a G/L line should not show identical fields.

Posting key = line ki qisam ka code. 40 matlab G/L debit, 50 matlab G/L credit. Ye code khud bhi kuch fields ke rules rakhta hai.

The assignment chain — one clean line to memorise

  • Variant → Company Code: OBC5 assigns the field status variant to the company code.
  • Group → G/L Account: each account’s company code segment (FS00) names its field status group.
  • Key → Line: every posted line carries a posting key (OB41).
  • Result: for each field, SAP merges the group’s status with the key’s status — using the priority rule next.

13 The priority rule — when two field statuses fight

One small rule, endlessly examined. Learn it with the reason, not by rote.

On a real line, the field status group may say “Cost Center: Optional” while the posting key says “Cost Center: Required”. SAP must pick one behaviour. It does not average them and it does not ask you — it follows a fixed priority order:

PriorityStatusWhy it sits here
1 (highest)SuppressA hidden field can hold no value — nothing else can overrule invisibility.
2DisplayA display-only field cannot accept typing, so “required” cannot be satisfied by the user — display wins over required.
3RequiredBetween “must fill” and “may fill”, the stricter rule protects the data.
4 (lowest)OptionalThe relaxed default — it wins only when nothing stricter is said anywhere.
Memory trick · “Chhupa, Dikha, Bharo, Chhoro”

Priority order in Roman Urdu: Chhupa (Suppress) sab se taqatwar, phir Dikha (Display), phir Bharo (Required — bharna zaroori), sab se kamzor Chhoro (Optional — chhor bhi sakte ho). In English: S–D–R–O — “Screens Demand Respect, Optional last.”

Worked mini-example

You post a debit (posting key 40) to the Rent account, whose field status group is EXPN:

FieldGroup EXPN saysPosting key 40 saysResult on screen
Cost CenterRequiredOptionalRequired — Required (3) beats Optional (4)
Trading PartnerSuppressOptionalSuppressed — Suppress (1) beats everything
AssignmentOptionalDisplayDisplay — Display (2) beats Optional (4)
Exam trap preview

Two favourites: (1) “Can a field be made required if it is suppressed in the posting key?” — No. Suppress has the highest priority; the field stays hidden. (2) “Where is the field status group stored?” — on the G/L account’s company code segment (SKB1), not on the chart segment and not on the company code itself. The company code only holds the variant (OBC5).

15 Exam traps

The mistakes C_TS4FI questions are designed to catch. Read these twice.

  • Trap 1 — “Change the company code currency after go-live.” The local currency (T001-WAERS) is fixed when the company code is created and cannot simply be changed once postings exist. It is a before-you-start decision.
  • Trap 2 — “Postings use the bank selling rate.” Standard FI translation uses exchange rate type M (average rate). B and G exist for specific bank processes.
  • Trap 3 — “A JPY amount is 100× too large — the rate must be wrong.” Blame decimal places (TCURX: JPY has 0 decimals), not the exchange rate.
  • Trap 4 — “Each company code needs its own chart of accounts.” False. One operating chart can be assigned to many company codes; but each company code has exactly one operating chart.
  • Trap 5 — “You can post directly to the group chart.” Never. Group and country charts are mapping / reporting views only, reached through the group account number (chart segment) and alternative account number (company code segment).
  • Trap 6 — “The account is in the chart, so it can be posted.” Only if the company code segment (SKB1) also exists for that company code. Chart segment alone (SKA1) is not postable.
  • Trap 7 — “Account group and field status group are the same thing.” The account group (OBD4) controls number ranges and the master-data screen. The field status group (OBC4) controls the posting screen. Different objects, different jobs.
  • Trap 8 — “Required beats Suppress.” The priority is Suppress → Display → Required → Optional. A field suppressed in the posting key stays hidden no matter what the group says.
  • Trap 9 — “The field status variant is assigned to the chart of accounts.” No — the variant is assigned to the company code (OBC5); the group is assigned to each G/L account (SKB1).
  • Trap 10 — “Parallel currencies can be added later and old documents will show values.” Parallel currencies (OB22) must be active before posting; historical documents have no values in a currency that was switched on afterwards.

Rule deciding whether a screen field is Required, Optional, Display or Suppressed.

One common chart for the whole group for consolidation and comparison; linked in OB13 to the operating chart.
Group Currency
Parallel currency in the parent company’s currency (type 30), for group reporting without later translation.
Hard Currency
Parallel currency (type 40) in a stable foreign currency, used in high-inflation countries.
Indirect Quotation
Rate written as foreign amount per 1 unit of local currency (1 PKR = 0.003597 USD); marked with “/” in OB08.
Ledger
One complete set of books under one set of accounting rules (leading ledger 0L); parallel currencies are set per ledger in S/4HANA.
Local Currency
Same as company code currency — the currency of the legal books; every posting is stored in it (amount field DMBTR).
Master Data
Standing data reused by transactions — G/L accounts, customers, vendors — as opposed to transaction (posting) data.

Enter exchange rates / define additional (parallel) local currencies / assign chart of accounts to company code.

Define chart of accounts / define account groups / define field status variant & groups / assign variant to company code / maintain posting keys.
Operating Chart of Accounts
The chart a company code posts in daily; exactly one per company code; one chart can serve many company codes.
Optional (field status)
Field may be filled or left empty; lowest priority (4) in the priority rule.
Parallel Currency
An additional currency in which every posting is valued at the same time as the local currency; set up in OB22.

2-digit code for the kind of posting line (40 = G/L debit, 50 = G/L credit, 31 = vendor credit…); carries its own field status; OB41, table TBSL.

Field must be filled before the document can be saved; priority 3.

Field is hidden and holds no value; highest priority (1) in the priority rule.

Currency of the business document itself (the invoice currency); amount field WRBTR.

The units in which an exchange rate is quoted (e.g. 1:1 or 100:1) per currency pair; OBBS, table TCURF.

17 Summary — the whole lesson on one screen

  • Currency: every posting is stored in the transaction currency (the invoice’s currency, WRBTR) and always translated into the local / company code currency (T001-WAERS, set in OX02, amount DMBTR) — plus any parallel currencies switched on in OB22 (types: 30 group, 40 hard, 50 index, 60 global company).
  • Currency settings = currency codes (OY03 / TCURC), decimal places (TCURX — JPY 0, KWD 3), rate types (OB07 / TCURV — M is the posting standard), translation ratios (OBBS / TCURF), and the rates themselves (OB08 / TCURR), in direct or indirect quotation.
  • Chart of Accounts (OB13, table T004, field KTOPL): the full list of G/L accounts; it also fixes the length of account numbers (max 10 digits). Assigned to company codes in OB62.
  • Three chart roles: operating (exactly one per company code; one chart can serve many company codes), group (linked via the group account number in SKA1), country (linked via the alternative account number in SKB1). Nobody posts in group or country charts.
  • G/L account master = chart segment (SKA1, once per chart) + company code segment (SKB1, once per company code); both are needed before posting; maintained together in FS00.
  • Account groups (OBD4, T077S): categories inside the chart that control the number range of new accounts and the field status of the master-data screen.
  • Field Status (posting side): the variant is defined in OBC4 and assigned to the company code in OBC5; each G/L account carries a field status group (SKB1); each line carries a posting key (OB41) with its own field status. The two merge by priority: Suppress → Display → Required → Optional.
