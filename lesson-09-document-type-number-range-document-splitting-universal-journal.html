New term — Posting

Posting means saving an accounting entry permanently into SAP's books. When you "post" in SAP, the system creates a document, gives it a number, and writes its lines into the database. (Posting = entry ko pakka karke system mein save kar dena.)

02 What is a Document in SAP?

Your journal entry from manual accounting — wearing a uniform, carrying an ID card.

In your Financial Accounting studies, the basic unit of bookkeeping is the journal entry: a date, some debit lines, some credit lines, debits equal credits. SAP uses exactly the same idea — it just calls it a document and gives it a strict structure.

New term — Document (Accounting Document)

The SAP name for one complete journal entry. A document is only saved when total debits = total credits. It is the smallest complete unit of accounting in SAP — you can never post "half an entry". (Document = aik mukammal journal entry — debit barabar credit.)

Every SAP document has two parts:

1 · Document Header — one per document

Information that applies to the whole entry: document number, company code, fiscal year, document type, posting date, document date, currency, reference, and who entered it. Stored in table BKPF.

2 · Line Items — two or more per document

The individual debit and credit lines: account, amount, cost centre / profit centre, text, tax code and so on. In classic ECC these lived in table BSEG; in S/4HANA every line is written into the Universal Journal, table ACDOCA (Part C of this lesson).

How is a document identified?

Three things together make a document unique — like a person's name + father's name + city:

  • Company Code — whose books? (field BUKRS)
  • Fiscal Year — which year? (field GJAHR)
  • Document Number — which entry? (field BELNR)

Document number 1900000042 can exist in company code PK01 and in company code PK02, and again in the next fiscal year — no clash, because the three-part key is different. Remember this: it explains why number ranges are defined per company code (Section 5).

Analogy — the invoice pad

Think of a manual invoice book. The header is the top of the page: date, invoice number, shop name. The lines are the items written below. You cannot tear out half a page and call it an invoice — and SAP cannot save half a document either.

New terms — Posting Date vs Document Date

Posting date decides which period and fiscal year the entry belongs to — SAP derives the period from it (Lesson 6). Document date is the date printed on the original paper (e.g. the vendor's invoice date). They can be different. Exam favourite

03 Document Type — the label on every document

Part A begins. Video: 06:26:05.

Imagine thousands of documents posted every day: vendor invoices, customer invoices, payments, salary entries, depreciation, goods receipts. If they were all mixed in one pile, finding and controlling them would be a nightmare. So SAP stamps every document with a two-character label — its document type.

New term — Document Type

A two-character code (like SA, KR, DR) that classifies a document by the kind of business transaction it represents. It is entered in the document header and controls important behaviour of the document — above all, which number range the document number comes from and which kinds of accounts may be posted to. (Document type = entry ki qism batane wala label — ye invoice hai, payment hai, ya aam G/L entry hai.)

Analogy — hospital file colours

In a hospital, patient files get different coloured folders: red for emergency, blue for OPD, green for surgery. The colour does not change the treatment inside — it tells everyone at a glance what kind of case this is and which register number series it follows. Document type is that colour on the accounting file.

The standard document types you must know

SAP delivers many ready-made types. You normally use these rather than inventing new ones. The pattern is easy: first letter hints at the area — K = vendor (German Kreditor), D = customer (Debitor), S = G/L account (Sachkonto), A = assets.

Memory trick — read the letters

Kreditor = vendor (think "K = Khareedari / supplier"), Debitor = customer ("D = Dena hai customer ne"), R = invoice (Rechnung), G = credit memo (Gutschrift), Z = payment (Zahlung). So KR = Kreditor + Rechnung = vendor invoice; DZ = Debitor + Zahlung = customer payment. Once you see the pattern, you can decode types you have never memorised.

What does a document type actually control?

  • Number range — every document type points to one number range; the document number is drawn from it at posting (Section 5).
  • Account types allowed — which kinds of accounts may appear in the document: Assets, D (customers), K (vendors), Materials, S (G/L accounts). A KR document, for example, is not allowed to contain a customer line.
  • Reverse document type — which type is used when this document is reversed (cancelled). If left blank, the same type is used.
  • Required fields — whether a reference number or document header text must be entered.
  • Control flags — e.g. whether negative postings are permitted, whether intercompany postings are allowed, whether a trading partner must be entered.
  • Authorization group — optionally restricts who may post with this type.
Trap 1 — Level of definition

Document types are defined at client level — one definition is valid for all company codes in the client. Number ranges, in contrast, are defined per company code. Exam questions love swapping these two levels.

04 Define a Document Type in OBA7 — step by step

Configuration T-code: OBA7 · also under SPRO → Financial Accounting → Financial Accounting Global Settings → Document → Document Types.

You rarely create brand-new types — projects usually copy a standard type and adjust it. But the exam tests whether you know what lives inside a document type, so let us open one.

  1. Run OBA7. You see the list of all document types in the client.
  2. Select a type (say SA) and open its details — or copy it to create your own (custom types usually start with a letter you choose, e.g. ZS).
  3. Fill the Properties: the number range key it should draw numbers from, the reverse document type, and the authorization group if needed.
  4. Tick the Account types allowed: Assets / Customer / Vendor / Material / G/L account.
  5. Set Control data: reference number required? Document header text required? Negative postings allowed? Intercompany postings?
  6. Save — the change goes into a transport request (Lesson 2) because document types are client-level configuration.

New term — Reverse Document Type

When you cancel (reverse) a document, SAP creates a new document with the opposite debit/credit lines — it never deletes the original. The reverse document type says which type that cancelling document carries. Classic pair: a KR vendor invoice reverses with type KG. (Reverse = entry ko delete nahi karte, uske bar-aks nayi entry banti hai.)

Trap 2 — "Document type is set per company code"

False. One definition, whole client. What does differ per company code is the number range behind it — the same type SA can draw numbers from range 01 in PK01 and a different interval in PK02, because ranges live per company code.

05 Number Ranges — every document gets a number

Configuration T-code: FBN1 · number range object: RF_BELEG.

Auditors hate gaps and duplicates in document numbers. SAP solves this with number ranges: pre-defined pools of numbers. When a document is posted, SAP takes the next free number from the pool that its document type points to.

New term — Number Range (Interval)

A defined block of document numbers — e.g. from 1900000000 to 1999999999 — maintained per company code and usually per fiscal year. Each interval has a short two-character key (like 01, 49, 51) which is what you enter inside the document type. (Number range = numbers ka aik block; har document ko isme se agla number milta hai.)

Internal vs external number assignment

Internal assignment — the normal way

SAP itself gives the next number, in strict sequence, at the moment of posting. The user never types a document number. Almost all FI documents work this way.

External assignment — the exception

The user types the number, and SAP only checks that it lies inside the interval and is not already used. Used when numbers must come from an outside system or a pre-printed book. In FBN1 the interval is flagged Ext.

Setting up a range in FBN1 — steps

  1. Run FBN1 and enter the company code.
  2. Choose Intervals and the fiscal year — ranges are normally created year-dependent: the same key (e.g. 01) gets a fresh interval for each fiscal year, so numbering restarts cleanly each year and old years stay untouched.
  3. Add the interval: from number, to number, and tick Ext only for external assignment.
  4. Make sure intervals for different types in the same company code and year do not overlap — a document number must stay unique within company code + fiscal year (Section 2), so two types may share one range, but two different ranges must never cover the same numbers.
  5. Save. Note: number range changes are not transported in the usual way — they are maintained directly in each system, because the "current number" is live data, not settings.

Trap 3 — Gaps in numbers

With internal assignment, numbers should follow in sequence — but gaps can still appear in real life: a posting that fails or rolls back after taking a number, or number range buffering (SAP pre-loads a block of numbers into memory for speed; unused buffered numbers are lost on restart). The exam point: a gap does not automatically mean fraud or a missing document — but every gap must be explainable. Also remember: two document types can share one number range — "every type needs its own range" is false.

Memory trick — type is the label, range is the token counter

At a bank counter you take a token. The document type decides which counter's queue you join (vendor invoices here, payments there). The number range is that counter's token machine. OBA7 writes the queue names; FBN1 fills the token machines — separately for every branch (company code).

06 Why Document Splitting exists — the problem

Part B begins. Video: 06:49:20. First, feel the problem — then the solution is obvious.

From Lesson 5 you know the Profit Centre: an internal unit (like a branch or product line) for which management wants its own profit report. And from Lesson 6, the Segment: a division of the company reported to the outside world (required by IFRS / GAAP segment reporting).

Quick recall — Profit Centre & Segment

Profit Centre = internal responsibility area; you want its own P&L and Balance Sheet. Segment = a reportable business division; in SAP it is normally derived automatically from the profit centre of a line. Both are called account assignment objects — extra "tags" carried on line items.

Now the problem. Your company has two profit centres: PC-LAHORE and PC-KARACHI. A vendor sends ONE combined bill of Rs 160,000 — Rs 100,000 of expenses belong to Lahore, Rs 60,000 to Karachi. You post it the simple way:

  • Debit Expense — Lahore — 100,000 (profit centre entered ✓)
  • Debit Expense — Karachi — 60,000 (profit centre entered ✓)
  • Credit Vendor — 160,000 (profit centre: ???)

The vendor line covers both branches, so you cannot tag it with one profit centre. Result: the P&L per profit centre works, but a Balance Sheet per profit centre is impossible — Lahore's books show an expense with no matching payable; Karachi's payable is hidden inside one mixed line. The vendor line does not balance to zero for either profit centre.

Analogy — two brothers, one electricity bill

Two brothers share a house but keep separate accounts. One WAPDA bill of Rs 16,000 arrives; the elder used Rs 10,000 of electricity, the younger Rs 6,000. If the bill stays as one line "payable 16,000", neither brother's personal ledger balances. The fair solution: split the payable — 10,000 owed by elder, 6,000 by younger. Each brother's books now balance alone. That is exactly what SAP does — automatically.

New term — Document Splitting

An automatic function of the General Ledger in S/4HANA: at posting time, SAP splits line items (like the vendor line above) across the profit centres / segments appearing in the document, in the same proportion as the lines that caused them — so that debits = credits for every single profit centre and segment separately. After splitting, you can produce a complete Balance Sheet per profit centre and per segment. (Document splitting = aik line ko profit centres ke hisaab se khud-ba-khud baant dena, taake har profit centre ki balance sheet alag ban sake.)

07 How Document Splitting works

Same invoice as Section 6 — now watch SAP fix it, and learn the three splitting rules.

The three splitting rules

RuleWhen it runsWhat it does
Active splitAt posting time, on the new documentSplits lines like vendor / customer / tax lines across the characteristics (profit centre, segment) of the "driving" lines — e.g. expense and revenue lines — in the same proportion.
Passive splitLater, when that item is cleared (e.g. the vendor is paid)The clearing document inherits the split of the original open item — the payment is divided between Lahore and Karachi exactly as the invoice was. No fresh decision needed.
Zero-balance clearingAt posting time, if a characteristic still does not balance to zeroSAP adds extra clearing line items on a special zero-balance clearing account so every profit centre / segment balances to exactly zero. Example: cash paid from Lahore's bank for Karachi's expense.
New terms — Splitting Characteristics & Item Category

Splitting characteristics are the fields the split is calculated for — normally Profit Centre and Segment (Business Area is also possible). Item category is SAP's internal label for what kind of line this is — balance sheet account, customer, vendor, cash, revenue, expense, asset, tax… The splitting rules are written per item category: e.g. "vendor lines (category 03000) split like the expense lines in the document".

New terms — Inheritance & Default Account Assignment

Inheritance: if a document has only one profit centre anywhere, lines without one simply inherit it. Default account assignment: if a characteristic is still empty after inheritance, SAP fills it with a fixed constant value you configured (e.g. a dummy profit centre) — so no line is ever left untagged.

Trap 4 — Splitting is not optional decoration

If document splitting is active and a line needs a profit centre / segment but gets none (no entry, no inheritance, no default), posting fails — SAP will not save an untagged line. That strictness is the whole point: reports per segment are only trustworthy if every line carries the tag.

08 Configuring Document Splitting — steps

SPRO path: Financial Accounting → General Ledger Accounting → Business Transactions → Document Splitting.

You do not need to memorise every click, but the exam expects you to know the sequence and the key ideas. The standard setup SAP delivers covers most cases — projects mostly activate and adjust.

  1. Classify G/L accounts — assign each account an item category (expense, revenue, balance sheet, cash…). This tells the splitting engine how each account's lines behave.
  2. Classify document types — assign each document type a business transaction and variant (e.g. vendor invoice = business transaction 0300, variant 0001). This tells SAP which splitting rules apply to documents of this type.
  3. Define splitting characteristics — choose the fields to split for: Profit Centre and Segment, and mark them as zero-balance characteristics (each value must balance to zero) and, if needed, mandatory.
  4. Define the zero-balance clearing account — the G/L account SAP uses for the automatic clearing lines of rule 3.
  5. Define default account assignment — the constant profit centre / segment used when a line would otherwise stay empty.
  6. Activate document splitting — switch it on at client level, then activate it per company code. Both switches are needed.
New term — Business Transaction (splitting)

Not the business event itself, but SAP's category for it inside the splitting rules: e.g. "vendor invoice", "customer invoice", "payment", "goods receipt". Combined with a variant (a numbered variation of the rules), it decides exactly how a document of a given type will be split. SAP delivers a standard splitting method — 0000000012 — containing the standard rules; most companies use it unchanged.

Trap 5 — Activation level

Document splitting is not activated per document type and not per ledger. It is switched on for the client and then for each company code. And documents posted before activation are not split afterwards — splitting happens at posting time only.

Trap 6 — Where does the Segment come from?

Users normally do not type the segment. It is derived from the profit centre — each profit centre master record carries its segment. Split by profit centre, and the segment follows automatically.

09 Entry View vs General Ledger View

The two faces of the same document — a favourite exam topic since S/4HANA.

Because of splitting, one document now exists in two views. When you display a document with FB03, you can switch between them:

Entry View — "what the user typed"

The document exactly as entered: 3 lines in our example. This view is based on the classic tables BKPF (header) + BSEG (lines). Vendor and customer open-item management also works on this view.

General Ledger View — "what SAP stored for reporting"

The document after splitting: 4 lines in our example, every line carrying its ledger, profit centre and segment. This view is read from the Universal Journal, ACDOCA, and can be shown per ledger.

Memory trick — two photographs

The Entry View is the photo you took of the entry. The G/L View is the photo after SAP's editor finished it — same event, more detail filled in. When a report looks "different" from the entry screen, you are simply looking at the other photograph.

10 The Universal Journal — one table for everything

Part C begins. Video: 07:38:00. This is the heart of S/4HANA Finance — and of this lesson.

First, the problem with the old SAP (ECC). Finance data was scattered across many tables, because each sub-area kept its own copy:

  • BSEG — G/L line items, but CO (Controlling) kept its own lines in COEP.
  • GLT0 and FAGLFLEXT — separate totals tables, updated alongside the lines.
  • BSIS / BSAS / BSID / BSAD / BSIK / BSAK — separate index tables for open and cleared items of G/L, customers and vendors.
  • Asset Accounting and the Material Ledger kept their own tables again.

Consequences: the same amount stored four or five times, FI and CO figures that had to be reconciled at month-end (and sometimes disagreed), and slow reporting because totals had to be maintained. You already know double-entry bookkeeping — imagine keeping the same journal in five notebooks and re-checking nightly that they agree. That was ECC.

New term — Universal Journal (Table ACDOCA)

S/4HANA's single line-item table for all of Finance: General Ledger, Controlling, Asset Accounting and Material Ledger lines are written into one table — ACDOCA. One line carries everything at once: ledger, company code, account, amount in several currencies, cost centre, profit centre, segment, asset, material… Because there is only one copy, there is nothing left to reconcile. (Universal Journal = saari finance entries ki aik hi bari register — ACDOCA. FI, CO, assets — sab aik jagah.)

What happened to the old tables?

  • BKPF (document header) — still exists, unchanged in its role.
  • BSEG — still exists for the entry view and for open-item management of customers/vendors, but the reporting truth for the G/L is ACDOCA.
  • Totals tables (GLT0, FAGLFLEXT) and secondary index tables (BSIS, BSAS, …) — no longer stored. SAP replaced them with compatibility views: they carry the old names, but behind the scenes they calculate their values live from ACDOCA, so old programs and reports keep working.
  • COEP (CO actual lines) — likewise replaced by a view on ACDOCA; CO postings are simply ACDOCA lines with CO fields filled.
New term — Compatibility View

A database view that wears the name of a removed table. Programs that used to read GLT0 still "read GLT0" — but the data is produced at that moment from ACDOCA. Like renaming the shop but keeping the old signboard, so old customers still find it.

Analogy — five notebooks vs one register

ECC was a shop with five notebooks: sales, expenses, stock, assets, and a totals notebook re-copied every night — and a monthly fight when they disagreed. S/4HANA keeps one big register (ACDOCA). Need a total? Add the lines on the spot — the HANA database is fast enough that pre-copied totals are unnecessary. One register, one truth, no nightly copying, no fights.

The benefits — the exam's favourite list

  • Single source of truth — FI and CO read the same lines; the old FI–CO reconciliation at period-end is gone.
  • Faster closing — no totals tables to update, no reconciliation steps; many period-end jobs simply disappeared.
  • Rich reporting — because every dimension sits on one line, you can slice the same data by ledger, profit centre, segment, cost centre, asset… without extra tables.
  • Multi-GAAP ready — all ledgers in one table means parallel accounting (Lesson 8) is just a filter on RLDNR.
  • Extension Ledger — S/4HANA also offers a special ledger type that stores only adjustment/delta postings on top of an underlying standard ledger (e.g. management adjustments) — possible only because ACDOCA is one table.
New term — ACDOCP

The planning twin of ACDOCA: plan data for Finance is stored in table ACDOCP, with (almost) the same structure — so plan vs actual comparisons read two tables built the same way. Exam favourite

Trap 7 — "BSEG was deleted"

Careful. The exam distinguishes: totals and secondary index tables were removed and replaced by compatibility views. BKPF and BSEG still physically exist (entry view, open items). "ACDOCA replaced BSEG completely" is the wrong answer; "ACDOCA is the single source for G/L reporting, merging FI and CO lines" is the right one.

Trap 8 — One ACDOCA line per posting?

No — one ACDOCA line per line item, per ledger. Post a document into ledgers 0L and 2L and every item appears twice in ACDOCA — once per RLDNR. That is how the G/L view "per ledger" in FB03 works.

12 One posting, end to end — all three parts together

Watch a single vendor invoice travel through everything you learned today.

  1. You open FB60 (Enter Vendor Invoice) and type the bill: expenses for Lahore 100,000 and Karachi 60,000, vendor credit 160,000.
  2. The screen proposes document type KR — from Part A you know what that controls: vendor + G/L account types allowed, and number range 51.
  3. You press Post. SAP checks: debits = credits ✓ · posting period open (Lesson 6) ✓ · field status satisfied (Lesson 7) ✓.
  4. Document splitting runs: the vendor line is split 100,000 / 60,000 across the two profit centres; segments are derived; every profit centre balances to zero.
  5. SAP draws the next number from range 51 for company code PK01: document 1900000042 is born. The header goes to BKPF, the entry-view lines to BSEG.
  6. Every line — entry view and split G/L view, for every assigned ledger — is written into the Universal Journal, ACDOCA, complete with cost centre, profit centre, segment and all currencies.
  7. From that second, reports — trial balance, profit centre Balance Sheet, segment report, CO cost centre report — all read this one document from this one table. No reconciliation, ever.
Memory trick — the passport office

Document type is the category stamp on the passport (visitor? worker?). Number range is the serial number printed on it. Splitting is the officer noting every city you will visit, not just the first. And ACDOCA is the central register where every passport ever issued is recorded — one register for the whole country.

14 Exam Traps — read these twice

Traps 1–8 appeared inside the sections. Here is the complete set for Lesson 9.

Trap 1 — Level of definition (types)

Document types are defined at client level (OBA7), valid for all company codes. Number ranges are per company code (FBN1). The exam swaps these constantly.

Trap 2 — Who assigns the number?

With internal assignment, SAP assigns the next number automatically at posting — the user never enters it. With external assignment, the user enters it and SAP only validates it.

Trap 3 — Shared ranges & gaps

Two document types can share one number range. And a gap in internal numbering (rollback, buffering) does not by itself prove a missing document — but intervals for the same company code + year must never overlap.

Trap 4 — Untagged lines fail

With splitting active, a line that ends up with no profit centre/segment (no entry, no inheritance, no default) cannot be posted. Splitting is strict, not decorative.

Trap 5 — Activation level (splitting)

Splitting is activated at client level + per company code — not per document type, not per ledger. Documents posted before activation are not split retroactively.

Trap 6 — Segment entry

The segment is normally derived from the profit centre, not typed by the user.

Trap 7 — "BSEG is gone"

False. BKPF and BSEG still exist. What disappeared as stored tables are the totals tables (GLT0, FAGLFLEXT) and secondary indexes (BSIS, BSAS…) — they are now compatibility views on ACDOCA.

Trap 8 — ACDOCA granularity

ACDOCA holds one line per line item per ledger. A document in two ledgers = every line twice, distinguished by RLDNR.

Trap 9 — Document identity

A document is uniquely identified by company code + fiscal year + document number — not by document number alone, and not by document type.

Trap 10 — Reversal deletes nothing

Reversing a document creates a new document (with the reverse document type, e.g. KR → KG). The original stays. SAP accounting never erases posted documents.

Trap 11 — FI–CO reconciliation still needed?

In S/4HANA, no. FI and CO post into the same ACDOCA lines, so there is nothing to reconcile. Any answer describing a period-end FI–CO reconciliation run belongs to ECC.

16 Summary — Lesson 9 in one page

  • Every posting in SAP is a document: one header (BKPF) + balanced line items, uniquely identified by company code + fiscal year + document number.
  • The document type (OBA7, client level) classifies the entry and controls the number range, the account types allowed, and the reverse document type. Decode the letters: K = vendor, D = customer, R = invoice, G = credit memo, Z = payment, S = G/L.
  • Number ranges (FBN1, per company code, usually per fiscal year) supply the document number — internally (SAP assigns) or externally (user assigns). Types can share a range; ranges must not overlap; gaps from buffering/rollback are explainable.
  • Document splitting divides lines like vendor/customer across profit centres and segments (active split at posting, passive split at clearing, zero-balance clearing lines when needed), so a full Balance Sheet per profit centre/segment is possible. It is activated at client level + per company code, uses item categories, business transactions and standard method 0000000012, and the segment is derived from the profit centre.
  • Result: every document has two faces — the Entry View (as typed, BSEG) and the General Ledger View (after splitting, per ledger, ACDOCA).
  • The Universal Journal (ACDOCA) is S/4HANA's single line-item table for FI-GL, CO, Asset Accounting and Material Ledger. Totals and index tables became compatibility views; FI–CO reconciliation disappeared; planning lives in ACDOCP.
