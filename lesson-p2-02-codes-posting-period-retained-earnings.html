02 Unique codes — why every entry needs its own identity

Segment 24:47 — Creating and saving unique codes for company data entries. First, the idea.

Almost everything you create in SAP Customizing is identified by a short code — a key. The company code has a 4-character key (BUKRS), the company a 6-character key, the chart of accounts a 4-character key, the posting period variant a 4-character key. The key is how SAP finds the entry everywhere: in tables, in assignments, in documents, in reports. Names can be long and can even repeat — keys cannot.

New term · Key / Unique code

A key is the short code that identifies one entry uniquely inside its table. “Unique” means: within the same client (the whole SAP system copy, from Part 1), no two entries of the same type may carry the same key. If you try to create company code PK01 when PK01 already exists, SAP stops you with an error — the entry already exists. The key is also called the entry’s primary key: the database itself guarantees there can never be two rows with the same one.

Har entry ka apna alag code hota hai — CNIC number ki tarah. Do entries ka code kabhi aik nahi ho sakta; SAP khud rok deta hai.

Why uniqueness matters in practice

  • Documents point at keys, not names. Every accounting document stores the company code key (e.g. PK01), not the company’s name. If two company codes could share a key, SAP would not know whose books a posting belongs to.
  • Assignments point at keys. When you assign a posting period variant to a company code in §9, you are really writing two keys side by side in a table. Wrong key = wrong company gets the setting.
  • Reports group by keys. Trial balance, balance sheet, tax reports — all select and total by key fields.
  • Keys are forever (almost). Once postings exist under a key, you cannot simply rename or delete it. That is why consultants choose codes carefully before creating entries — the next section is all about that.

Memory trick · Code = CNIC

Pakistan mein har shakhs ka CNIC number unique hota hai — naam aik jaisay ho saktay hain, number nahi. SAP mein bhi bilkul yehi rule hai: naam repeat ho sakta hai, code nahi. Jab bhi “unique code” parhain, CNIC yaad kar lein.

03 Choosing good codes — the rules before you type

Thirty seconds of thinking before creating an entry saves hours later. The rules consultants actually follow.

Rule 1 — Respect the length of the key field

ObjectKey fieldLengthExampleCreated in
Company CodeBUKRS4 charactersPK01OX02
CompanyRCOMP6 charactersPKGRP1OX15
Chart of AccountsKTOPL4 charactersPKCAOB13
Posting Period VariantVNAME (variant name)4 charactersPK01 / Z001OBBO
Fiscal Year Variant—2 charactersK4OB29

You cannot type a 5-character company code — the field simply will not accept it. Length is fixed by SAP’s data definition, not by your preference.

Rule 2 — Stay out of SAP’s own namespace

SAP delivers standard entries whose keys usually start with digits or plain letters (variant 0001, chart INT, fiscal year variant K4). Customer-made entries traditionally start with Z or Y — the reserved customer namespace — or with your own meaningful prefix. Two benefits: your entries never collide with a future SAP delivery, and anyone can see at a glance “this one is ours, not standard”.

Rule 3 — Make the code speak

  • Meaningful beats random: PK01 (Pakistan, unit 01) is understood instantly; XQ7Z is forgotten by lunch.
  • Keep a pattern across objects: if the company code is PK01, naming its posting period variant PK01 too is a common, tidy habit — one glance shows which variant belongs to which company code (you will do exactly this in §7).
  • Leave room to grow: numbering 01, 02, 03… lets a second and third company code join later without breaking the pattern.
  • Never reuse a retired code for a different object — old documents and reports still carry the old key.
Exam trap · “Can the key be changed later?”

The exam loves this: a key is the entry’s identity. You can change an entry’s name and details freely, but the key itself is not edited — the practical way to “rename” is to create a new entry with the new key, re-do the assignments, and (only if unused) delete the old one. Once real postings exist under a company code, even that is no longer realistic. Choose carefully, once.

04 Step by step — creating & saving company entries with unique codes

Segment 24:47, hands on. Creating the company and company code entries, and saving them so they truly exist.

You already know these two transactions from Part 1 · Lesson 5 and Part 2 · Lesson 1 — OX15 (Company) and OX02 (Company Code). What is new today is the discipline of creating with a fresh unique code and saving correctly, including the transport request that appears in a Customizing system.

Before you create — check the code is really free

  1. Open OX02. On the overview screen, use Position / search or press F4 in the company code field and search for the code you plan to use (e.g. PK01).
  2. If the search finds nothing — the code is free. If it finds an entry — stop: pick another code, or open the existing entry instead of creating a duplicate (SAP would refuse anyway, as you saw in §2).
  3. The database-level check also works: SE16N on table T001, filter BUKRS = PK01. Zero rows = free code.

Creating the entries

  1. Company first (OX15): choose New Entries, type your unique 6-character company code (e.g. PKGRP1), company name, city, country and language. The Company is the consolidation unit from Part 1 — the group-level identity.
  2. Company code (OX02): choose New Entries (or use Copy from a similar existing company code — §8 shows the same copy idea for variants). Type the unique 4-character code (e.g. PK01), the company name, city, country, currency (e.g. PKR) and language. Currency and language are set here, at creation — remember from Part 1 that the company code currency is the local currency of its books.
  3. Press Enter — SAP validates the key immediately. A duplicate key errors here, before anything is stored.
  4. Complete the address details screen if it appears, then press Save (Ctrl+S).
  5. The transport pop-up: in a Customizing (development) system, saving asks for a Customizing request — create a new request with a sensible description (e.g. “FI: Company code PK01 created”) or select your existing one, and confirm. As you learned in Part 2 · Lesson 1: cancelling this pop-up cancels the save — the entry would not exist.
  6. Read the status bar: “Data was saved” / the entry appears in the overview list. Only now does the entry truly exist.

Verify immediately — the 30-second habit

  1. Leave the transaction (/n) and re-enter OX02 — or run SE16N on T001 with BUKRS = PK01.
  2. Your entry must appear with the exact name, currency and country you typed. If it is not there, the save did not complete (most often: the transport pop-up was cancelled).
Analogy · Registering a newborn

Pehle check karte hain ke ye naam/number pehle se registered to nahi (free-code check). Phir form bharte hain (details), phir form jama karte hain (Save + transport request — the “file number” your paperwork travels under). Sirf form bhar lena registration nahi hai — jama karana registration hai. Aur ghar aa kar record dobara check karna (verify) samajhdari hai.

05 Posting Period Variant — the gatekeeper of the calendar

Segment 27:35 begins. First the idea, in plain words — you met this in Part 1 · Lesson 6; today you build one.

Accounting works in posting periods — normally the 12 months of the fiscal year, plus special periods for year-end adjustments. At any moment, some periods are open (you may post into them) and the rest are closed (posting is refused). Who decides which periods are open? A Posting Period Variant.

Key term · Posting Period Variant (PPV)

A Posting Period Variant is a named set of rules (a 4-character code, e.g. PK01 or the SAP standard 0001) that states, for each account type, which posting periods are currently open. The variant itself holds no company data — it is a reusable rulebook. You assign the variant to one or more company codes (OBBP), and from then on, transaction OB52 opens and closes periods through that variant. One variant can serve many company codes that share the same open/close rhythm.

Posting Period Variant aik rule-book hai: kis mahine mein posting ho sakti hai, kis mein nahi. Company code ko ye rule-book assign ki jati hai — baghair assignment ke rule-book almari mein pari rehti hai, lagu nahi hoti.

Do not confuse the two “variants” Exam favourite

Fiscal Year Variant (FYV)Posting Period Variant (PPV)
Question it answers“What does our year look like?”“Which periods may I post into right now?”
ContentNumber of periods, where each period starts/ends (calendar layout)Open/closed ranges per account type
Defined inOB29 (e.g. K4 = calendar year, 12 periods + 4 special)OBBO
Assigned inOB37 (to company code)OBBP (to company code)
Used daily in— (background calendar)OB52 — open/close periods

Easy sentence to remember: the Fiscal Year Variant draws the calendar; the Posting Period Variant locks and unlocks its pages.

Analogy · Library ke timings

Fiscal Year Variant library ka saal bhar ka calendar hai — kab khulti hai, chhuttian kab hain. Posting Period Variant roz ka gate-keeper hai: aaj ka din kis section ke liye open hai — bachon ka section (customers), reference section (vendors), ya sab ke liye band? Calendar alag cheez hai, gate-keeper alag — dono ki zaroorat hai.

06 Inside a variant — account types, period ranges & the + row

Before creating one, learn to read the OB52 grid — the screen where a variant does its daily work.

Open any variant in OB52 and you see a grid. Each row is one rule: for this account type, in this fiscal year, periods from X to Y are open. The columns:

ColumnMeaning in simple words
VariantWhich rulebook this row belongs to (the PPV key, e.g. PK01)
Account typeWhich kind of posting this row controls — see the table below
From account / To accountOptional: limit the row to a range of account numbers (blank = all accounts of that type)
From period 1 / To period 1The normal open range — the periods ordinary users may post into
From period 2 / To period 2A second open range, only usable by users with the row’s authorization group — typically for the accountants closing the books
From year / To yearThe fiscal year(s) this row applies to
Authorization groupWho may use period range 2 (checked against the user’s authorizations)

The account types — one letter each

CodeAccount typeControls postings to…
+Valid for all account typesEverything — the master row (see below)
AAssetsAsset accounts (fixed assets)
DCustomersCustomer (debtor) accounts — “D” from Debitors
KVendorsVendor (creditor) accounts — “K” from Kreditoren
MMaterialsMaterial / stock accounts
SG/L accountsGeneral ledger accounts — “S” from Sachkonten (G/L accounts in German)
Key rule · The + row is compulsory

Every variant must contain a row with account type +. The + row is the fallback rule for everything. In practice, companies often open periods only through the + row (one simple rule for all), and add specific rows (D, K, S…) only when one type needs different treatment — for example, keeping vendors (K) open one extra week while customers (D) are already closed. A more specific row beats the + row for its account type; anything without its own row follows +.

Memory trick · + pehle, baaki baad mein

Variant ki table hamesha + wali row se shuru karein — ye “sab ke liye” wali buniyadi row hai. Specific rows (D, K, S) sirf tab banayein jab kisi aik type ko alag treatment chahiye. Aur letters yaad rakhne ke liye: D = Debtor (customer), K = Kreditor (vendor), S = Sachkonto (G/L), A = Assets, M = Materials.

07 Step by step — creating & configuring a variant (OBBO)

Segment 27:35, hands on. Creating the Posting Period Variant using its transaction code.

New term · OBBO

OBBO is the Customizing transaction “Define Variants for Open Posting Periods”. Here you create the variant’s identity — its unique 4-character code and name. The variant created here is still empty of company meaning: it becomes real for postings only when its periods are maintained (OB52) and it is assigned to a company code (OBBP). In the IMG (SPRO) the same screen lives under Financial Accounting → Financial Accounting Global Settings → Ledgers → Fiscal Year and Posting Periods → Posting Periods → Define Variants for Open Posting Periods. The variant list is stored in table T010O.

The steps

  1. Type OBBO in the command field and press Enter. The overview of existing variants opens — you will see SAP’s standard variant 0001 here.
  2. Click New Entries.
  3. In the Variant field, type your unique code. Following the tidy pattern from §3, use the same code as your company code: PK01. (Check first that PK01 is not already listed as a variant — uniqueness rule from §2 applies here too.)
  4. In the Name / Description field, type a clear name, e.g. “Posting Period Variant – PK01”. The name is for humans; the code is for SAP.
  5. Press Save (Ctrl+S). Answer the Customizing request pop-up (create/select your request, confirm). Watch for “Data was saved.”
  6. Go back to the overview: your variant PK01 must now be listed next to 0001. It exists — stored in table T010O.
Illustration — OBBO · Define Variants for Open Posting Periods · New Entries
Variant  : PK01 ← unique 4-char key (same as company code — tidy pattern)
Name     : Posting Period Variant – PK01
Existing standard entry for comparison:
Variant  : 0001   Name: Posting Period Variant 0001 (SAP standard)

Exam trap · Creating ≠ configuring ≠ assigning

Three different acts, three different places — the exam tests them separately. Create the variant in OBBO. Configure its open periods in OB52. Assign it to the company code in OBBP. If a scenario says “the variant was created but postings are still blocked for the company code”, the missing step is almost always the assignment — or the periods were never opened in OB52.

08 Copying a variant — the consultant’s shortcut (OBBO)

Segment 37:56, first half. Why professionals rarely type a variant from zero.

Typing every OB52 row by hand for a new variant is slow and error-prone. The professional way: copy a variant that already works — usually SAP’s standard 0001, or your own proven variant — give the copy a new unique code, adjust the few rows that differ, and save. Copying carries over the variant’s period rows, so the copy starts life complete instead of empty.

The steps

  1. Open OBBO and select the source variant (click its row, e.g. 0001).
  2. Choose Copy (the “Copy As…” function / F6 in the classic GUI menu: Edit → Copy As).
  3. SAP shows the entry with the source code. Overwrite the code with your new unique code, e.g. PK01, and adjust the name. The new code must not exist yet — the uniqueness rule again.
  4. Press Enter, then Save (Ctrl+S) and confirm the Customizing request.
  5. Open the copy in OB52: the period rows came with it. Adjust only what your company does differently (for example, your fiscal year, or an extra authorization-group range).
  6. Save again in OB52 — period rows live in table T001B, keyed by variant.
Exam trap · Never modify the standard variant 0001

Changing 0001 directly is a classic beginner mistake and a favourite exam scenario. SAP can overwrite delivered entries in an upgrade, and every company code still using 0001 would silently inherit your changes. The correct professional pattern is always: copy 0001 → your own code → change the copy. The same pattern applies to company codes, charts and fiscal year variants.

09 Assigning the variant to the company code (OBBP) & opening periods (OB52)

Segment 37:56, second half. The step that makes the variant real — then the daily screen it powers.

New term · OBBP — assignment

OBBP is the Customizing transaction “Assign Variants to Company Code” for posting periods. An assignment is a simple two-key row in a table — here table T010P — that says: company code PK01 uses posting period variant PK01. Each company code gets exactly one posting period variant; one variant may serve many company codes. Until this row exists, the company code has no open/close rulebook at all.

Assigning — the steps

  1. Type OBBP and press Enter. The assignment overview lists company codes and their current variants.
  2. Find your company code PK01 (use Position/search if the list is long).
  3. In its Variant column, enter PK01 — or press F4 and pick your variant from the list (the F4 list is exactly the variants defined in OBBO, stored in T010O).
  4. Press Save (Ctrl+S), confirm the Customizing request, and check for “Data was saved.” The assignment row now sits in table T010P.

Now open the periods — OB52

  1. Type OB52. Enter your variant PK01 on the selection screen (in some systems OB52 opens the grid directly — then filter by variant).
  2. Check the + row: set the fiscal year and the normal open range, e.g. periods 1 to 12 for your current year, so everyday posting works.
  3. If you copied the variant in §8, most rows are already correct — verify them instead of retyping.
  4. Save. From this moment, posting into an open period succeeds; posting into a closed period fails with a “period is not open” error — the variant is now actively guarding your company code.

OBBO mein rule-book likhi gayi, OB52 mein uske pages par timings likhay gaye — lekin jab tak wo book PK01 ke desk par rakhi nahi jati (OBBP assignment), PK01 ke staff ke liye wo exist hi nahi karti. Assignment wohi “desk par rakhna” hai.

10 Retained earnings — where the year’s profit finally sleeps

Segment 39:32 begins. You met retained earnings in Part 1 · Lesson 8; here is the practical heart of it.

Your accounting knowledge already knows this story. All year, income and expense accounts (the Profit & Loss accounts) collect the period’s activity. At year-end their balances cannot simply vanish — the net result, profit or loss, belongs to the owners and must move into the Balance Sheet, into equity, as retained earnings (the accumulated profit the company keeps instead of distributing). Accountants call the yearly movement balance carryforward.

Key term · Retained Earnings Account

The Retained Earnings Account is the one Balance Sheet (equity) G/L account that receives the net balance of all P&L accounts at year-end carryforward. SAP does not guess which account this is — you must tell SAP, per chart of accounts, in transaction OB53. No assignment in OB53 = the carryforward has nowhere to go, and year-end closing cannot complete correctly. In OB53 the link is made through the P&L statement account type: the standard type is X, and each type can point to exactly one retained earnings account per chart.

Saal bhar ka nafa-nuqsan aakhir mein aik hi khaate mein ja kar jama hota hai — Retained Earnings. SAP ko batana parta hai ke wo khaata konsa hai; khud se andaza nahi lagata. Ye batana hi OB53 hai.

Three facts the exam returns to again and again

  • One per type, per chart: in OB53, for one chart of accounts and one P&L statement account type (X), there is exactly one retained earnings account. You may define additional types (e.g. A, B) if different groups of P&L accounts must carry into different retained earnings accounts — an advanced option; the standard setup uses only X.
  • It is a Balance Sheet account: the retained earnings account itself is created as a Balance Sheet account (in FS00), never as a P&L account — it receives the P&L result; it is not part of it.
  • The assignment is per chart, not per company code: OB53 is maintained at Chart of Accounts level. Every company code using that chart inherits the same retained earnings assignment — define once, use many times, the variant principle again.

11 The series rule — the retained earnings number must live in the equity / liability series

Segment 39:32, the detail everyone misses. This is where Part 2 · Lesson 1’s “series” comes back.

Recall from Part 2 · Lesson 1: in OBD4 every account group owns a series — a From–To number interval in the chart (stored in table T077S). A G/L account can only be created with a number inside its group’s interval. The retained earnings account is a G/L account like any other, so it obeys the same law — and that creates a practical rule you must check before OB53:

Key rule · Series pehle, assignment baad mein

The retained earnings account must belong to a Balance Sheet account group whose series covers the equity / liabilities numbers of your chart — in a typical plan, the 3xxxxx series (liabilities & equity), for example group EQTY owning 300000–399999, with the retained earnings account at 331000. If the account number you want does not fall inside any suitable Balance Sheet group’s interval, FS00 will refuse to create the account there — fix the series in OBD4 first (widen or add the group interval), then create the account, then assign it in OB53.

Series (typical plan)Account groupBelongs there
100000 – 199999ASST — AssetsCash, receivables, fixed assets
200000 – 299999LIAB — LiabilitiesPayables, loans, tax payable
300000 – 399999EQTY — EquityShare capital + Retained Earnings (e.g. 331000)
400000 – 499999REVN — RevenueSales and other income (P&L)
500000 – 699999EXPN — ExpensesCosts and expenses (P&L)

Notice the geography: retained earnings sits with the owners’ claim on the business — the equity block of the liability side of the Balance Sheet. That is exactly what your accounting knowledge expects: profit kept in the business increases equity. The “liability series” wording simply reflects that in many charts the whole liabilities + equity side is planned as the 2xxxxx–3xxxxx block, and the retained earnings account must be numbered inside it — never inside the revenue or expense series.

The failure you will meet if you skip this check

  • You try to create account 331000 in FS00 under a P&L group (or a group whose interval ends at 299999) → SAP errors: the number is outside the group’s interval.
  • Or the account exists but in the wrong series (say 430000, inside Revenue) → your Balance Sheet structure breaks: retained earnings would report inside income.
  • The cure is never “force it” — the cure is: check OBD4 → fix the series → create in the right group → assign in OB53.
Memory trick · Nafa malik ka hota hai

Retained earnings ka number hamesha equity wali gali mein hoga — kyunke saal ka nafa company ke maalikon ka hota hai. Agar number revenue ya expense wali series mein nazar aye, samajh lein ghalti hai: nafa aamadni nahi hota, nafa maalikiat (equity) hai.

12 Step by step — assigning the retained earnings account (OB53)

Segment 39:32, hands on. The assignment itself takes one minute — if §11 was checked first.

New term · OB53 & P&L statement account type X

OB53 is the Customizing transaction “Define Retained Earnings Account”. Its screen is a small table with three columns: Chart of Accounts, P&L statement account type, and Account. The P&L statement account type is a one-character label stamped on P&L accounts (in their chart-level master data) that tells the carryforward “accounts of my type close into this retained earnings account”. SAP’s standard type is X — in the standard setup, all P&L accounts carry type X and OB53 has exactly one row: chart → X → retained earnings account. The assignment is stored in table T030 (standard account determination).

Pre-check (30 seconds, from §11)

  1. The retained earnings G/L account exists in the chart — e.g. 331000 “Retained Earnings”, created in FS00 as a Balance Sheet account in the equity group, inside the 3xxxxx series.
  2. Your P&L accounts carry P&L statement account type X (the standard). If they carry a different type, OB53 needs a row for that type instead.

The assignment — the steps

  1. Type OB53 and press Enter. The retained earnings table for all charts opens.
  2. Click New Entries.
  3. Chart of Accounts: enter your chart, e.g. PKCA (F4 helps — the list comes from OB13 / table T004).
  4. P&L statement account type: enter X.
  5. Account: enter the retained earnings account number, e.g. 331000. Press Enter — SAP checks that the account exists in that chart. A non-existent account is refused here.

Exam trap · OB53 is chart-level, not company-code-level

A very common wrong answer: “retained earnings is assigned per company code.” No — OB53 is maintained per Chart of Accounts. Two company codes sharing chart PKCA automatically share the same retained earnings account assignment. If an exam scenario gives two company codes with the same chart but “different retained earnings accounts”, that is impossible through OB53 — the difference would have to come from different charts or different P&L statement account types.

14 Exam traps

The exact confusions C_TS4FI questions are built on, from today’s topics.

Trap 1 · Duplicate code “should work because the name is different”

False. Uniqueness is about the key, not the name. Two entries may share a name; they may never share a key in the same table and client. SAP rejects the second creation with “entry already exists”.

Trap 2 · Fiscal Year Variant vs Posting Period Variant

FYV (OB29) = the calendar layout of the year. PPV (OBBO) = which periods are open. OB52 belongs to the PPV world; OB37 assigns the FYV; OBBP assigns the PPV. Mixing any pair of these four is the single most common wrong answer in this topic area.

Trap 3 · “The variant was created, so posting must work”

Creation (OBBO) alone changes nothing for a company code. The chain is: create → open periods (OB52) → assign (OBBP). A missing assignment or a missing + row leaves postings blocked even though “the variant exists”.

Trap 4 · Editing standard variant 0001

Professionals copy 0001 and change the copy. Editing the delivered standard risks upgrade overwrites and silently affects every company code still using 0001.

Trap 5 · Retained earnings assigned per company code

No — OB53 is per Chart of Accounts. And per chart + P&L statement account type there is exactly one retained earnings account; the standard type is X.

Trap 6 · Retained earnings as a P&L account, or in the revenue series

The retained earnings account is a Balance Sheet (equity) account, and its number must sit inside the equity / liability series of its account group (OBD4). Putting it in the revenue series (4xxxxx) or defining it as a P&L account breaks the carryforward logic and the Balance Sheet structure.

Trap 7 · One variant, one company code only?

The relationship is one-to-many in the useful direction: one PPV can serve many company codes; each company code has exactly one PPV. Company codes with the same period rhythm should share a variant — that is the point of making it a separate object.

15 A–Z glossary

Every technical term from this lesson, in simple words.

Assignment (OBBP / OB53)
A two-key table row that connects a setting to the object that uses it — variant → company code (T010P), chart + type → retained earnings account (T030). Created but unassigned settings do nothing.
Authorization group (OB52)
A label on an OB52 row; only users whose authorizations include that group may use the row’s second period range — typically reserved for the closing team.
Balance carryforward
The year-end program that closes P&L account balances into the retained earnings account, so P&L starts the new year at zero and the result lives in equity.
BUKRS
The database field name of the company code key — 4 characters, e.g. PK01 (table T001).
Chart of Accounts (KTOPL)
The list of all G/L accounts of an organisation, identified by a 4-character key; defined in OB13, stored in T004.
Customizing request
The transport request a Customizing save is recorded in. Cancelling its pop-up cancels the save itself.
Fiscal Year Variant (FYV)
The calendar layout of a year — how many periods and where they fall (OB29, e.g. K4). Not the same as the Posting Period Variant.
Key / unique code
The short code identifying one entry in its table; must be unique in the client. Names may repeat — keys may not.
OB52
“Open Posting Periods” — where a variant’s open period ranges per account type are maintained (table T001B).
OB53
“Define Retained Earnings Account” — assigns one retained earnings account per chart of accounts and P&L statement account type (table T030).
OBBO
“Define Variants for Open Posting Periods” — creates the Posting Period Variant itself (table T010O).
OBBP
“Assign Variants to Company Code” — assigns a Posting Period Variant to a company code (table T010P).
P&L statement account type
A one-character type stamped on P&L accounts that steers their carryforward; the standard type is X, pointing to the chart’s retained earnings account in OB53.
Posting Period Variant (PPV)
A 4-character rulebook stating, per account type, which posting periods are open. Created in OBBO, maintained in OB52, assigned in OBBP.
Retained Earnings Account
The Balance Sheet (equity) G/L account that receives the net P&L result at carryforward; its number must sit in the equity / liability series of its account group.
Series (number range)
The From–To account-number interval an account group owns in OBD4 (table T077S). An account’s number must fall inside its group’s series.
T001 / T004 / T010O / T010P / T001B / T030 / SKA1
The tables behind today’s screens: company codes / charts of accounts / period variants / variant assignments / open periods / retained earnings determination / G/L accounts per chart.

16 Summary — the whole lesson on one screen

If you can say these lines from memory, you own this lesson.

  • Codes are keys: every Customizing entry is identified by a short unique code (company code 4 chars, company 6, chart 4, PPV 4). Names may repeat; keys never do. Choose meaningful codes in the customer namespace, check the code is free before creating, and remember — keys are not edited later.
  • Create + save: OX15 / OX02 entries exist only after Save with the Customizing request confirmed. Cancelling the request pop-up cancels the save.
  • Posting Period Variant: the rulebook of open periods, per account type (+, A, D, K, M, S), with a normal range and an authorization-group range. The + row is compulsory. Do not confuse it with the Fiscal Year Variant (the calendar itself).
  • The PPV chain: create in OBBO → maintain periods in OB52 → assign to the company code in OBBP. Professionals copy 0001 instead of building from zero or editing the standard.
  • Retained earnings: the Balance Sheet equity account that receives the year’s net P&L result at carryforward. Its number must live in the equity / liability series of its OBD4 account group (typically 3xxxxx).
  • OB53: one retained earnings account per chart of accounts + P&L statement account type (standard X) — chart-level, not company-code-level.
  • Verify everything: OB13 + T004 for the chart, FSP0 + SKA1 + T030 for the retained earnings account, OBBO/OBBP/OB52 + T010O/T010P/T001B for the variant chain. Saved? Assigned? Findable again? — then it is done.
